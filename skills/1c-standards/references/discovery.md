# Подбор норм средствами v8std

Для design/change/review это основной способ находить нормы за пределами
baseline registry. Не нужно проверять каждое слово или читать весь корпус.
Единица поиска — затронутый метод, запрос или описанный механизм изменения.
Исходник получай через разрешённый EDT/index/revision-aware маршрут и сохраняй
target, sourceRef и границы каждого фрагмента. Не загружай весь большой проект.

## По коду

Выбери по живому контракту подбор норм по BSL/SDBL для каждого затронутого фрагмента
оцениваемой фазы, включая enclosing условия, влияющие на смысл изменения.
Для proposal передавай конкретный предлагаемый код; для review — точную ревизию.
Baseline также нужен, если удаление/замена кода влияет на проверяемое требование.
Не подменяй результат описанием diff, когда доступен сам относящийся к нему код.

Сначала проверь живую schema и описания ограничений. Бюджет рекомендаций может
быть общим для diagnostics и standards. Если метод больше лимита, выделяй
смысловые части по разрешённым структурным фактам, сохраняя сигнатуру и нужные
условия/транзакционную границу в соответствующих фрагментах или context запросе.
Не обрезай метод до первых допустимых символов; отметь покрытые части и оставшийся
пробел. Учитывай лимит вместе с добавленным контекстом. Секреты замени безопасными
значениями, сохранив значимые операции; если это скрывает существенный факт,
сохрани ограничение проверки.

В ответе объединяй `standards`, сигналы и полезные диагностические ссылки.
`confidence`, даже `1.0`, — эвристика ранжирования, не вероятность нарушения.
Сигнал может возникнуть на комментарии, литерале или методе другого receiver.
Отсутствие сигнала/кандидата также не означает соответствия. Язык пока служит
подсказкой, если контракт не подтверждает отдельный analyzer.

Диагностические IDs из ответа не являются результатом запуска EDT/BSL LS.
Если они относятся к затронутому механизму, получи связанные нормы через
пакетную расшифровку с точными IDs и namespace анализатора, без дублей. Сохраняй
частоты реальных findings отдельно, если они нужны отчёту; повторять ID ради
повторного нормативного текста не нужно. Уже возвращённые связи переиспользуй.
Особенно проверь этот маршрут, если shortlist содержит только diagnostics:
связанные стандарты могут не поместиться в общий бюджет рекомендаций.
Расшифровка реальных analyzer findings использует тот же инструмент, а оценка
достоверности следует [контракту диагностики](../../1c-routing/references/diagnostics.md).

## По контексту

Для design без конкретного кода, metadata, удаления/rename и фактов за пределами
snippet используй подбор требований по контексту: краткий предмет изменения,
проверенные mechanisms и подходящие collections. Размер входа определяй по
живому контракту; mechanisms описывай понятными терминами, не рассчитывай на
понимание внутренних policy tags. Выбирай collections по предмету задачи:

| Collection | Для чего |
| --- | --- |
| `v8std` | Общие стандарты BSL/SDBL и метаданных |
| `corporate` | Рабочие правила применимой области, включая документы типа `rule` |
| `yaxunit` | Проектирование/авторинг unit-тестов, patterns и справочные API cards |
| `vanessa` | Gherkin/UI-сценарии, patterns и справочные tool cards |

Проверь по живому контракту, какие типы и collections покрывает подбор по коду.
Нельзя считать его достаточным для corporate `rule` и framework `reference`,
если этот маршрут их не возвращает. Context-подбор нужен также для норм и
справочных условий, которые не выводятся из программного фрагмента.
Для относящихся к задаче corporate/framework требований используй отдельный
context запрос по соответствующему corpus, дополняя подбор BSL/SDBL. Один общий
top-N на несколько collections не гарантирует присутствия каждой.
Не загружай framework corpus, если задача его не затрагивает.

Gherkin не передавай в подбор BSL/SDBL: для него используй context с
целью/структурой сценария и затронутыми механизмами, затем exact page/section.
Специальную карточку pattern/API используй только в поддерживаемой коллекции;
иначе читай точный документ/раздел. API/tool card даёт факты о контракте, но не становится
обязательной нормой только из-за попадания в подбор.

Начинай с компактного набора, например 5 context-кандидатов. Ответ имеет coverage
`ranked_candidates_not_exhaustive`, если сервер явно не гарантирует иное. При пропуске
известного существенного механизма уточни context, раскрой диагностическую связь
или выполни адресный поиск; увеличение top-N без причины не доказывает
полноты. Не продолжай раскрывать все фоновые связи корпуса.

## От кандидата к проверяемой норме

Объединяй результаты по canonical ID/heading с baseline из policy. Сохраняй
короткий учёт кандидатов: selector, источник поиска/фрагмент, решение и основание.
Для явно постороннего результата достаточно объяснить несоответствие контексту;
для потенциально применимого получи полный точный текст и необходимые условия.
Если context/candidate уже содержит достаточный полный текст с подтверждённой
identity, повторное чтение не требуется. Бюджет, pagination, truncation и reuse
следуют [контракту MCP](mcp.md).

- `applicable`: условие нормы относится к проверяемому target/переходу. Укажи
  нормативную силу по точному тексту и проектным условиям. Новый selector добавь
  в `additionalRequirements`, даже если такого механизма/ID нет в registry.
  В `mechanisms` передавай только имена из живой schema policy; тему за пределами
  этого словаря сохрани в context/basis, не создавай произвольный tag.
- `not_applicable`: сохрани конкретную причину — например, это только комментарий,
  receiver имеет другой контракт или условие нормы отсутствует. Рейтинг не причина.
- `unresolved`: сохрани недостающий факт/текст и его влияние. Существенная
  неопределённость не допускает полного заключения о соответствии и зависимой
  записи; при ревью допустим частичный отчёт.

В `additionalRequirements` передавай только подтверждённые нормативные selectors,
`strength: mandatory|recommended` и `basis`: точный источник/редакцию, условие
применимости и scope. Diagnostic ID сам по себе туда не переносится. Условия
отдельных пунктов одного документа сохраняй в evidence; если их сила различается,
разделяй точными headings либо сохраняй более сильный уровень и явно отмечай
различие условий. Базовая mandatory норма не понижается дополнительной записью.

Policy связывает additions с digest и требует их строки в том же ledger, но не
получает ответы v8std самостоятельно и не доказывает честность отбора кандидатов.
Пропущенный или необоснованно отклонённый кандидат остаётся возможным дефектом
работы агента. В отчёте различай покрытие изменённого кода, разбор полученных
кандидатов и выполнение выбранных норм; не заявляй исчерпывающий поиск по корпусу.

Существующие policy selections относятся к oneC/YaXUnit. Vanessa pattern можно
включить в additions, если его условие относится к этому target. Для отдельного
Gherkin-артефакта не выдумывай `artifact: bsl` или YaXUnit mechanisms ради digest:
сохраняй нормы, применимость и результаты в статическом отчёте Vanessa workflow.
У bundled policy пока нет отдельного selector/validator для Gherkin; такой отчёт
не называй результатом `validate_compliance`.

Переиспользуй подбор при неизменных scope, коде/контексте и корпусе. Перед записью
обновляй его при существенном изменении proposal; после записи повторяй для
отличий actual result от проверенного предложения. Новый sourceRef всегда требует
актуального compliance evidence, даже если подбор и нормативный текст сохранены.
