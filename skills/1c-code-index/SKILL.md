# 1C code-index

Apply the [knowledge gate and authority roles](../1c-routing/SKILL.md) and use an
exact alias from the selected profile. Follow the
[binding and coverage checks](references/analysis.md#completeness-and-freshness)
for the needed text or enrichment layer.

Use a [bounded indexed query](references/analysis.md) for the fact needed. Read
known objects, symbols or ranges directly. Start unknown discovery with one search
matched to the clue. Default to up to 10–20 hits, exact scope, brief fields and
depth 1 for graph exploration. Use the [relay controls](../1c-routing/references/toolsets.md#calling-the-relay)
for targeted schemas and native results. Check partial pages, omitted sections
and deduplication.

A knowledge card or an indexed fact is evidence for its own scope. When a
conclusion or action needs a missing current fact, read the exact method, metadata
or source position of the known target through the assigned EDT. Use scoped
references or call hierarchy for a missing live relation. A filtered
`search_in_code` answers lexical questions within its coverage. Restrict the
handoff to affected facts, including significant dirty changes. An EDT read can
settle a specific target fact. Keep conclusions that require missing broader
index coverage unverified. Expand only to resolve a gap that affects the answer.

## Reuse-gate

Assess each new technical operation by purpose, including small operations such
as choosing a default or filling an object. Simple syntax and composition of
confirmed operations need no separate search. Keep mandatory knowledge readiness
for every dependent phase, including all ordinary work in KORA.

- **Known contract:** use current evidence for the applicable revision, library,
  platform and execution context. Read only missing facts.
- **New operation:** state the purpose in 1–3 terms. Search selected knowledge when
  enabled for an unresolved reuse choice and the current alias when source evidence
  is needed. Add dependencies only on evidence. Verify platform/BSP contracts
  directly through $1c-platform-docs without repeating the knowledge search.
- **Substantial effects:** verify consumers and restrictions when public API,
  supplier ownership, access, data, transactions or client/server boundaries
  matter. For a narrow low-risk gap, choose one targeted search.

Use the applicable mandatory project API or wrapper, including when a direct
library call is shorter.
Verify candidates against purpose, parameters, result, export/access, context,
ownership, version, permissions, transactions, writes, events and lifecycle.
Exclude candidates marked
`recommendation: avoid` from new calls. Check up to five relevant candidates
by default, using depth-1 references for ambiguity. Expand only for a specific
coverage, conflict or impact question.

Choose between applicable reuse, narrow adaptation and new code by verified
behavior, effects and maintenance cost. Use a compatible project mechanism when
adequate. Adapt within its contract and authorized ownership. New code needs a
specific reason a candidate is absent, unsuitable or disproportionate to adapt.
For a nonexported method, check in-scope reuse options before duplicating it.
Changing a shared or other-owned API requires its own scope and consumer review.
An absence claim requires ready, complete coverage of that scope. If a conflict
affects the choice, use the assigned authority for each disputed fact. An
unresolved requirement or authority conflict blocks the dependent choice.

Stop at a sufficient choice. Retain the decision, material alternatives, selected
collections/alias, revision and verification limits. Keep broad discovery on the
assigned index route and protected source reads within the authorized authorities.
