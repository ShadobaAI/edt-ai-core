# Recovery отказа EDT model gate до записи

Применяй только при выполнении разрешённого изменения через назначенный EDT.
Workflow является общим для проектов и определяется фактическим отказом,
а не версией сервера. Подтверди по живому контракту тот же отказ до mutation.
Это ограниченное исключение из правила одной коррекции,
а не повтор любой неуспешной записи.

## Условия входа

Все условия должны выполняться одновременно:

- Отказал именно `create_metadata` или `modify_metadata`.
- Ответ содержит `isError: true`, `structuredContent.success: false` и точное
  сообщение:
  `Project is building: the model or the reference index is still being computed. Please wait and retry.`
- Для установленного контракта подтверждено, что этот отказ происходит до
  записи. Нет выполняющегося write job, признаков `mutationCommitted`,
  `mutationOutcomeUnknown` или другого неопределённого исхода.
- Сохраняются разрешённые repository, EDT instance/URL, project и область задачи.

Timeout, обрыв связи, неоднозначный ответ, pending write job, другой текст ошибки
или неподтверждённый момент отказа не подходят. Применяй основной workflow
проверки неизвестного исхода; не повторяй writer по этому исключению.
`list_projects: ready` допускает этот recovery, но не доказывает готовность модели
к записи. Read-only ревью не разрешает выполнять recovery с повтором writer.

## Адресное восстановление

1. Сохрани отказавший tool, полные исходные arguments, guards и счётчик попыток
   для конкретной намеренной операции. Подтверди точные имя/path/open/EDT nature
   того же проекта и неизменный binding. Смена binding или потеря готовности
   останавливает зависимые действия до восстановления обязательных предпосылок.
2. Установи верхнего владельца по уже разрешённому FQN: для
   `Catalog.X.Form.F.Group.G` это `Catalog.X`. При создании ещё не существующего
   верхнего объекта допустим владелец непосредственно предшествующей успешной
   сохранённой записи, только если она подтверждена в этой сессии, относится к
   тому же проекту и разрешённой области задачи, а её владелец ещё разрешается в
   EDT. Без такого владельца останови recovery. Не угадывай соседний объект.
3. Выполни `revalidate_objects` назначенного EDT один раз на попытку, передав
   точный project и непустой `objects` только с этим владельцем. Нельзя опускать
   `objects` или передавать пустой список. Проверь завершённый success и что
   владелец указан как Validated, а не Not found/Skipped. Если возвращён job,
   следи за тем же job до подтверждённого исхода; ack недостаточен. При timeout
   не запускай новую revalidation или writer, пока прежний исход неизвестен.
4. Через тот же EDT проверь точный target: отсутствие для create, текущие
   значения для modify и применимость всех сохранённых guards. Обнови требуемый
   focused diagnostic baseline. Если эффект уже присутствует, проверь результат
   без повторной записи. Изменившиеся state/guards прекращают этот recovery и
   требуют reconciliation по основному workflow; не меняй отказавшие arguments
   внутри recovery. Правила счётчика при таком переходе определены ниже.
5. Повтори неизменённую запись один раз, сохранив все guards. Подтверждённое
   сохранение и обычные post-diagnostics/result compliance завершают recovery
   этой операции и позволяют продолжить задачу. Если снова получен тот же
   доказанный отказ до записи, повтори шаги 1–5 в пределах **трёх recovery-попыток
   всего**: максимум три повтора writer после исходного отказа. Счётчик сохраняй
   между ходами; переименование или повторная постановка той же операции его не
   сбрасывает. Другая самостоятельная операция имеет собственный бюджет.

Иной отказ, неизвестный исход, непройденная revalidation/диагностика или потеря
обязательной предпосылки прекращает recovery. Для async revalidation допустимо
наблюдать существующий job; новый writer требует подтверждённого завершения.
Не выполняй revalidation профилактически после каждой успешной записи.

## После трёх одинаковых отказов

6. Останови записи. Подготовь конкретный scope для `clean_project`: project/path,
   отказавшая операция и результаты трёх попыток; укажи, что clean сбрасывает
   результаты сборки и запускает пересборку. По общей
   [action policy](../../1c-routing/references/action-policy.md) проверь реальное
   разрешение пользователя на cleanup этого проекта. Переиспользуй уже данное
   разрешение того же scope; при его отсутствии запроси только недостающее
   согласование. Поручение изменить код или наличие этого workflow не разрешает
   clean. До получения разрешения clean не выполняется.
7. После разрешения выполни `clean_project` точного проекта **один раз** по живой
   schema/guide. Подтверди окончательный исход rebuild/job и ready того же
   проекта. Timeout clean/rebuild требует проверки существующей операции,
   повторный clean запрещён. Инвалидируй затронутые факты и заново проверь target,
   guards и focused baseline. Если эффект отсутствует и исходные arguments/guards
   остаются применимыми, допустим **один последний повтор writer**. Изменившиеся
   guards требуют reconciliation, а не автоматической подмены payload. Дальнейший
   отказ или неопределённость останавливает восстановление; clean и бюджет не
   повторяются. Если эффект уже есть, проверь его без нового writer.

Этот этап доступен только после трёх допустимых recovery-попыток с тем же
отказом, а не после timeout, неизвестного владельца или ошибки диагностики.
Предельное число writer-вызовов: исходный, три повтора до clean и один после
разрешённого clean. Каскадные rename/delete, database/launch и другие эффекты
сохраняют свои требования готовности и scope.

Reconciliation выполняется по основному workflow с актуальными source/guards,
применимостью требований и proposal. Запись с изменённым payload не является
разрешённым повтором по этому исключению. Если после reconciliation продолжается
та же намеренная операция, сохрани счётчик writer и факт clean: смена hash,
новый proposal или переформулировка задачи не создают новую операцию. Любой её
следующий writer расходует оставшийся общий лимит; после clean остаётся максимум
один writer независимо от перехода между workflows. Если последний writer уже
был выполнен, переход к reconciliation не даёт ещё одного повтора или clean.

Не перезапускай EDT, не выполняй whole-project revalidation, не обходи model gate
и не меняй сериализованные файлы. В отчёте сохрани счётчик, владельца, outcomes
revalidation/write/clean, результаты проверок и причину остановки.
