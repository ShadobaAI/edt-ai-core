# KORA 3.1. Концепция целевого окружения ИИ-разработки 1С:CRM

**Редакция:** 3.1, 12 октября 2026 года  
**Назначение:** целевая концепция и требования для последующего проектирования, реализации и приёмки окружения команды 1С:CRM.  
**Статус:** архитектурное описание, готовое для декомпозиции на задачи реализации. Готовность этой концепции **не означает**, что новые интеграции установлены, безопасны или уже выдержали эксплуатационные испытания.  
**База анализа:** текущее окружение, коммит `0309b8169e1a5ddd160ed1e1ef612107babd129b`. Состояние развёрнутых экземпляров MCP, EDT, БСП, Codex и OpenViking этим анализом не подтверждено.

## 1. Решение и границы

### 1.1. Для чего создаётся KORA

KORA меняет **инженерное поведение Codex** при работе с крупной, непрерывно изменяемой CRM-конфигурацией 1С:

1. Codex **не должен повторно реализовывать** подходящие механизмы CRM, БСП, платформы и существующих настроек только потому, что не нашёл их при локальном поиске.
2. Codex **не должен переусложнять** реализацию защитами от неподтверждённых сценариев, новыми абстракциями, универсальными обёртками, обработчиками исключений и ветками поведения без доказанной потребности.
3. Codex **не должен повторно исследовать** уже достоверно изученные возможности, если их применимость к текущей задаче установлена.

Результат: корректный код с минимальной **обоснованной** сложностью и меньшими затратами разработчика 1С на поиск, проверку, исправления и ревью. Токены, длина diff, доля переиспользования и число вызванных MCP являются диагностическими, а не конечными метриками.

**Не цель:** всегда использовать старый API, всегда писать меньше строк, документировать всю БСП/CRM, передать Codex самостоятельное право изменять общую ИБ либо заменить ревью человека.

### 1.2. Принятые архитектурные решения

| ID | Решение | Последствие |
| --- | --- | --- |
| D-01 | **`1c-ssl-mcp` исключается из целевого окружения**; база возможностей БСП (SSL) в Markdown + OpenViking является его заменой | Удаляются сервер, прежние маршруты, doctor-пробы и тесты; старый SSL-поиск не является штатным fallback |
| D-02 | База CRM, база БСП и проверенный опыт команды хранятся **в одном командном Git-репозитории знаний** | Git определяет опубликованную редакцию; OpenViking является только поисковым индексом |
| D-03 | Два контроля: **переиспользование** и **достаточность**; они выполняются при выборе и проверке решения | Это правила поведения, не отдельные агенты и не вызовы MCP для каждого оператора |
| D-04 | `code-index`, `crm-edt` (EDT-MCP), `v8std`, `crm-policy`, `bsl-ls` сохраняют свои функции; `1c-docs-mcp` остаётся источником документации платформы | Не создаются дублирующие индексы кода, анализаторы и корпуса нормативных документов |
| D-05 | SDD и План реализации **соразмерны классу риска** | Маленькая задача не превращается в многоступенчатый документооборот |
| D-06 | Codex получает только **технически ограниченное чтение** командного OpenViking | Автоматическая запись сессий, персональная память и пути публикации недоступны агенту |
| D-07 | MCP общей ИБ является **отдельной, необязательной для первого пилота** интеграцией только для разрешённых служебных сведений | Нет произвольных запросов, выполнения кода или записи/чтения прикладных данных |
| D-08 | Допускается полная замена текущих AGENTS, Skills, config, installer, policy glue и doctor **без обратной совместимости** | Переносить старые правила ради совместимости не требуется; полезные гарантии сохраняются по смыслу |
| D-09 | **OpenViking обязателен для штатной работы Codex.** Если он недоступен, небезопасен или его индекс не подтверждён, выдаётся ошибка и работа останавливается по принципу обязательного `code-index`; автоматического резервного поиска по Markdown/другим инструментам нет. **Прямое чтение Markdown-карточек допускается только по явному запросу пользователя.** | Недоступность OpenViking означает `blocked` независимо от сложности задачи. Адресное чтение `.md` по запросу не снимает блокировку штатного процесса; уточнение версии API через EDT не заменяет поиск по OpenViking |

### 1.3. Основные инженерные ограничения 1С

- CRM содержит легаси, проектные обёртки БСП и доработки типового кода. Общие методы могут иметь много потребителей; локальная реализация иногда безопаснее изменения общего контракта.
- Одновременно используются различные ветки и рабочие копии, возможны незакоммиченные изменения. Общая ИБ отражает **своё состояние**, а не произвольную ветку.
- Существенны клиент/серверный контекст, доступность метода, права и RLS, транзакции, обработчики и подписки, обмены, побочные эффекты, версия платформы/БСП, производительность и обновляемость типовой конфигурации.
- Исходники CRM и YaXUnit расположены в разных EDT-проектах; нельзя выдавать тестовую конфигурацию за production-реализацию.
- Разработчик 1С остаётся владельцем требований, решения по спорным контрактам и итогового diff. Codex не получает широких прав только ради удобства автоматизации.

## 2. Что выявлено в текущем состоянии окружения

Это сведения **из текущего состояния окружения**, а не результат проверки рабочего стенда:

| Компонент снимка | Наблюдение | Решение при переработке |
| --- | --- | --- |
| `PROJECT_AGENTS.md` | Основной CRM-проект `EDT`, тестовое расширение `EDT.YAXUNIT`; `crm-edt` является разрешённым владельцем live-изменений. Запрещено обходить MCP чтением сериализованных исходников через shell | Сохранить разграничение исходников и право записи через EDT |
| `skills/1c-code-change/SKILL.md` | `Domain-aware reuse gate` проверяет прежде всего новое самостоятельное поведение, но явно исключает простые локальные действия | Расширить до выбора **новой технической операции по смыслу**; не вводить поиск на каждый оператор |
| `config.toml.template`, Skills, doctor, tests | `1c-ssl-mcp` предусмотрен как опциональный источник БСП | Полностью удалить из целевого комплекта; заменить маршруты на каталог БСП/OpenViking |
| `skills/1c-code-index/SKILL.md`, `PROJECT_AGENTS.md` | При неполном или устаревшем индексе предписано прекращать индексный маршрут, без повторного discovery через EDT | Ввести ограниченное риск-ориентированное восстановление нужных фактов, исключающее ложное подтверждение отсутствия API |
| `crm-policy`, `v8std`, `crm-reviewer`, YaXUnit | Уже имеются нормы, проверка соответствия, независимое ревью, диагностические и тестовые маршруты | Переиспользовать; убрать только избыточные процедурные требования, не теряя нормативных гарантий |
| `install.cmd`, `doctor.mjs`, `mcp/installed-config.mjs`, `mcp/doctor-probes.mjs`, `tests/test-documentation-mcp.mjs`, `README.md`, GUI | Установка, пробы и документация зависят от перечня MCP и названий маршрутов | Миграция затрагивает весь комплект; не ограничиваться одним `config.toml` |
| `policy/profile-manifest.json` | Профиль Skills/agents/policy подписан по составу/хешам | При замене собрать **согласованный новый профиль** и проверить единообразие поставки |

**Вывод:** проблема не сводится к отсутствию инструмента БСП. Нужны новые правила выбора решения, проверенная семантическая база возможностей и целостная переработка маршрутизации Codex.

**Явное несовместимое наследие:** текущий `PROJECT_AGENTS.md` требует держать доступным весь набор MCP tools, включая добавленные обновлением, а конфигурация `crm-edt` сохраняет полную поверхность. Для OpenViking и MCP общей ИБ это недопустимо: новый профиль вводит **сервисно-специфичные** границы доступа и повторную проверку поверхности tools после обновлений. Старое глобальное «не скрывать tools» удаляется; нужные операции EDT остаются доступными в рамках разрешений и согласований. Это сознательное изменение политики, допустимое без обратной совместимости.

## 3. Целевая архитектура

```text
                          Разработчик 1С
                    задача / SDD / критерии
                                │
                            Codex
           ┌────────────────────┼─────────────────────┐
           │                    │                     │
   Правила KORA            Поиск знаний       Проверка текущих фактов
  + локальный план      (только чтение)       и изменение исходников
           │                    │                     │
  Контроль reuse         OpenViking            code-index (read)
  Контроль scope            │                  crm-edt (live + write)
  Достаточность             │                  bsl-ls (diagnostics)
  Review diff        Git Markdown:            1c-docs-mcp (платформа)
           │          - CRM                    v8std + crm-policy (нормы)
           │          - БСП/SSL
           │          - опыт
           └────────────────────┬─────────────────────┘
                                │
                  Проверки → принятие diff
                                │
             Контролируемая публикация опыта в Git

           Дополнительно, отдельно от основного потока:
          ограниченный read-only MCP общей ИБ разработки
             (сведения о состоянии именно этой ИБ)
```

**Профили готовности:** `ready` возможен только при доступном и безопасном read-only OpenViking, подтверждённой актуальности опубликованного индекса, доступных базах БСП/CRM и обязательных source tools. Недоступность OpenViking, неподтверждённая полнота индекса либо нарушение границ чтения означает **`blocked`**: режима `degraded` с поиском по Git Markdown нет. MCP общей ИБ имеет отдельный независимый статус готовности и не влияет на обязательность OpenViking.

**Путь знаний:** проверенный Markdown → публикация Git → контролируемая индексация → OpenViking (поиск) → выбранная карточка → подтверждение нужного контракта для рабочей ветки.

**Путь изменений:** задача → определение границ → поиск/выбор механизма → минимальный план → изменение только в назначенной рабочей копии через разрешённый writer → диагностика/тесты → проверка diff → принятие разработчиком.

Никакой источник не заменяет другой автоматически. Индекс помогает обнаружить кандидат; карточка объясняет назначение и ограничения; EDT сообщает состояние обслуживаемого проекта; общая ИБ сообщает состояние общей ИБ.

### 3.1. Распределение ответственности по инструментам

| Инструмент/источник | Сфера ответственности | Не является |
| --- | --- | --- |
| База CRM и БСП | Поиск возможностей **по намерению**, условия применения, варианты | Полной копией исходников или доказательством наличия API в любой ветке |
| OpenViking | Семантический поиск, короткий результат, ссылка на опубликованную карточку | Нормативным редактором Git, общим writer для Codex, вторым индексом CRM-кода |
| `code-index` | Известные функции, текстовые/структурные кандидаты, статические связи и потребители в проверенном индексе | Источником истины о незакоммиченных изменениях, доказательством отсутствия динамических вызовов |
| `crm-edt` | Live-метаданные/исходники назначенного EDT-проекта, целевые изменения и диагностика | Средством исследования всего CRM без ограничения области |
| `bsl-ls` | Фокусированная BSL-диагностика и семантика | Заменой интеграционных тестов или проверок EDT |
| `1c-docs-mcp` | Документация платформы 1С | Заменой базы БСП или текущих проектных контрактов |
| `v8std` + `crm-policy` | Нормативные требования и обоснованный выбор применимых правил | Поиском прикладных реализаций CRM/БСП |
| MCP общей ИБ | Только явно разрешённые служебные runtime-сведения | Подтверждением текущей ветки, доступом к бизнес-данным, программным запуском кода |

### 3.2. Принцип достоверности

**Истина определяется вопросом, а не порядком поиска:**

1. **Что действительно есть в моей ветке/рабочей копии?** Назначенный EDT-проект, включая релевантные незакоммиченные изменения; indexed evidence используется только при подтверждённой применимости индекса.
2. **Что делает проектный API?** Актуальное объявление и существенные условия в той же ветке плюс релевантные потребители; опубликованная карточка может сократить проверку при подтверждённой совместимости.
3. **Как должна работать платформа/БСП?** Соответствующая версия документации/карточки и проверенная фактическая реализация, если продукт модифицировал типовую библиотеку.
4. **Какие правила обязательны?** Действующие требования проекта и применимые нормативные разделы `v8std`/`crm-policy`.
5. **Как настроена общая ИБ?** Только состояние общей ИБ с указанной конфигурацией, датой/контекстом чтения.

Противоречие разных версий не объявляется ошибкой само по себе: сначала установить **объект, ревизию и смысл** каждой записи. При неразрешимом противоречии, критичном для выбора, остановить соответствующее изменение. Утверждение «не найдено» не доказывает «не существует» вне проверенной области поиска.

## 4. Разработка: один процесс, разная глубина

### 4.1. Типы задач

| Класс | Типичный случай | Постановка/планирование | Проверки и согласования |
| --- | --- | --- | --- |
| **L**: локальный низкорисковый | Локальная правка, не меняющая контракт, права, схему, внешнее взаимодействие или транзакции | Постановка и критерий готовности достаточны как краткая SDD; план внутренний, по необходимости | Точечная диагностика/проверка; разработчик принимает diff |
| **M**: изменение поведения | Новая локальная логика, запрос, изменение нескольких взаимосвязанных операций | Краткая SDD/описание границ и проверяемых результатов; компактный План, если больше одного значимого решения | Применимые нормы, проверки поведения; ревью до принятия |
| **H**: существенный риск | Публичный контракт, схема данных, права, интеграция, общий легаси, архитектура, опасная миграция | Отдельная согласованная SDD и План существенных этапов; при необходимости ADR | Проверка потребителей/рисков, независимый reviewer, расширенные релевантные тесты и явное решение разработчика |

Наличие слова «тест» или маленького diff не делает изменение L. Класс определяется **возможными последствиями**, а не количеством строк. Для каждого класса обязательны корректность, управление доступом, сохранение требований и честное указание непроведённых проверок.

### 4.2. Рабочий цикл Codex

1. **Проверить обязательные источники и установить задачу:** перед штатной работой проверить доступность OpenViking, допустимость его read-only доступа и подтверждённую публикационную ревизию (§ 5.4, § 8); при ошибке прекратить процесс, не подменяя поиск другим источником. Затем установить требования, затронутый EDT-проект, границы, критерии принятия и существенные изменения рабочей копии. Не расширять запрос самостоятельно.
2. **Выделить способности:** какие действия реально нужны для SDD (например, вычислить реквизит, уведомить пользователя, обновить регистр, вызвать внешний сервис). Объединить одинаковые операции.
3. **Проверить готовое:** применить Контроль переиспользования (§ 5) к каждой новой по смыслу операции; различать использование, допустимую локальную адаптацию и новый код.
4. **Выбрать объём:** применить Контроль достаточности (§ 6) к дополнительным веткам, проверкам и абстракциям. Учесть существующие гарантии API и реальные последствия отказа.
5. **Планировать только нерешённое:** сформировать или уточнить План уровня M/H, указать существенные изменения, зависимости, проверки и точки согласования.
6. **Выполнить через разрешённый writer:** изменять нужные объекты без несанкционированных побочных рефакторингов; после нового технического вопроса локально повторить нужный контроль, не пересоздавать весь план.
7. **Проверить результат:** критерии SDD, применимые нормы, диагностика, нужные тесты и фактический diff; убрать оправданно не нужную сложность.
8. **Передать на ревью:** короткий отчёт о результате, переиспользованных API/существенных исключениях, проверках и пробелах. Публикация полезного опыта через отдельное контролируемое решение команды.

**Запрет на ритуалы:** нет обязательного полного обхода MCP, повторной проверки уже подтверждённого контракта, схемы состояний для каждого оператора, отдельного журнала поисковых вызовов и нового согласования тривиальных локальных решений.

### 4.3. Остановка планирования и делегирование

Задача делится, пока остаётся **самостоятельное нерешённое решение** (выбор контракта, модели данных, способа интеграции, критичная зависимость). Когда метод, ограничения и проверка известны, дальнейшая декомпозиция прекращается. Пример статуса ветки: `ГОТОВЫЙ_API`, `НАСТРОЙКА`, `ЧАСТИЧНО_ГОТОВО`, `ЛОКАЛЬНО_НОВОЕ`, `НУЖЕН_КОНТРАКТ`, `БЛОКИРОВКА`; эти метки не становятся обязательным сериализованным документом.

Разработчик отдельно согласует изменение публичных контрактов, схемы, безопасности, интеграций, высокорисковую миграцию либо существенное отклонение от SDD. Обычные решения в утверждённой области выполняются без микросогласований. Несколько агентов и `crm-reviewer` применяются по выгоде от независимости/разделения работы, а не постоянно.

## 5. Контроль переиспользования: основной механизм против дублирования

### 5.1. Граница применения

Контроль выполняется **при выборе новой технической операции по назначению**, даже если её можно написать парой строк BSL. Например: получить свойство с умолчанием, сообщить пользователю, заполнить значение, построить представление, разрешить путь к файлу, выполнить проектную проверку, изменить настройки или связать объекты.

Нет отдельной проверки для оператора `Если`, присваивания, локального цикла либо уже подтверждённой операции: **не синтаксис определяет потребность в поиске, а неизвестный способ решить смысловую задачу**. Повторное использование найденного метода в другом месте текущей задачи не создаёт новых поисковых действий.

### 5.2. Выбор режима

| Режим | Когда | Достаточное действие |
| --- | --- | --- |
| **Известный** | Подходящий механизм уже достоверно известен в применимом контексте | Сразу выбрать; не повторять поиск |
| **Быстрое уточнение** | Новый для задачи механизм, низкий риск, совместимость неочевидна | Один сгруппированный смысловой поиск по CRM/БСП, до нескольких кандидатов; проверить ровно недостающее |
| **Углублённый** | Общий API, изменение типового кода, права, данные, транзакции, клиент/сервер, сложный побочный эффект | Подтвердить контракт, потребителей и последствия в текущей ветке, сравнить с локальной альтернативой |

**Ориентир начальной настройки:** одна смысловая выдача с максимум пятью кандидатами на группу операций; по умолчанию подробно рассматривать не более трёх релевантных. Это ограничения стоимости **пилота**, а не запрет получить нужные доказательства для рискованного решения.

### 5.3. Алгоритм выбора

1. Проверить, не известен ли в текущем контексте **проектный обязательный API/настройка**. Такой контракт имеет приоритет, если его использование требуется соглашениями CRM.
2. Если подходящий механизм неизвестен, искать в общем каталоге CRM + БСП **по задаче**, а при известном имени — также точное имя. Для платформенной функции пользоваться штатной документацией платформы, не заставляя поиск OpenViking дублировать её.
3. Для найденных кандидатов установить назначение, входные/выходные параметры, контекст выполнения, существенные побочные эффекты, область применения и принадлежность. Похожее название не является доказательством пригодности.
4. Если карточки нет, есть сомнение в версии либо возможна проектная обёртка, выполнить **ограниченный** поиск `code-index`, при необходимости проверку текущего контракта `crm-edt`. Нельзя проводить обязательный последовательный поиск по всем инструментам.
5. Оценить три реализации: **переиспользовать**, **локально адаптировать**, **написать новое**. Менять общий API ради одной задачи допускается только когда это безопаснее и соответствует её границам.
6. Остановиться, когда найдено корректное и достаточно проверенное решение. При низком риске после разумного поиска допустима небольшая локальная реализация без абсолютного доказательства отсутствия аналога; это решение не объявляется уникальным для всей CRM.

Из всех причин нового кода достаточны: контрактная несовместимость, другой клиент/серверный контекст, недопустимые побочные эффекты, слишком высокая цена изменения общего легаси, неподходящая версия либо отсутствие подходящего кандидата в **проверенной области** поиска.

### 5.4. Ошибки обязательных источников и устаревание поиска

- **OpenViking недоступен, отказал в доступе, нарушена граница read-only либо индекс не соответствует подтверждённой публикации:** сообщить диагностическую ошибку, перевести штатный процесс в `blocked` и **не продолжать разработку**. Автоматический переход к прямому чтению Markdown, `code-index`, EDT или прежнему SSL-MCP как замене OpenViking запрещён. После восстановления обязательны успешная проверка доступа и синхронизации индекса.
- **Прямое чтение Markdown-карточек:** допускается только при **явном запросе пользователя** на чтение, анализ или изменение конкретных `.md`. Это отдельное разрешённое действие, а не способ восстановить штатный поиск или обойти `blocked`. Автоматическое чтение карточек из Git/локального каталога ради поиска API запрещено. Штатная загрузка `AGENTS.md`/Skills и работа уполномоченного процесса публикации знаний к этой оговорке не относятся.
- **`code-index` недоступен:** применять установленный для него механизм ошибки и не подменять discovery обходом CRM через EDT. Если индекс доступен, но не отражает конкретную ветку или незакоммиченные изменения, его находки и пустая выдача не подтверждают live-факты: допустим **узкий EDT-запрос** на уже известный символ, контракт/метаданные или зависимость. Это проверка конкретного факта, не резервный индекс.
- **Нет другого обязательного факта при работоспособных обязательных источниках:** блокировать зависимое решение при риске нарушения контракта, безопасности, данных или требований. Низкорисковый локальный выбор может допускать ограниченный результат с явным пробелом доказательств; этот принцип **не отменяет** обязательность OpenViking.
- **EDT-проект не тот / недоступен writer:** не изменять исходники и не обходить ограничение shell, соседней рабочей копией или общей ИБ.

Если источники противоречат друг другу, сначала проверить их ветку, момент и покрытие. Нельзя выбрать удобный результат и скрыть конфликт. Точечное подтверждение известного контракта через EDT требует обновления старых Skills/AGENTS, но **не заменяет** недоступный `code-index` или OpenViking.

## 6. Контроль достаточности: основной механизм против переусложнения

**Правило:** перед добавлением **нетривиальной** проверки, `Попытка/Исключение`, `fallback`, альтернативного алгоритма, общего вспомогательного метода, расширения API или ветки поведения Codex должен понимать: *какое требование, инвариант, достижимое состояние или реальное последствие этим закрывается?*

| Основание | Решение |
| --- | --- |
| Прямое требование, действующий контракт, стандарт безопасности/целостности | Реализовать |
| Реально достижимый отказ с существенными последствиями: внешние данные, права, транзакция, обмен, потеря данных | Обработать соразмерно границе и последствиям |
| Редкий, но достижимый критичный сбой | Не игнорировать только по низкой вероятности |
| Состояние исключено установленным контрактом и путями вызова | Не дублировать контроль автоматически |
| Воображаемое состояние без подтверждённой достижимости либо существенных последствий | Не добавлять защитный сценарий |
| Абстракция, параметризация или универсальность «на случай будущих требований» | Не реализовывать |

**Бремя обоснования лежит на добавляемой сложности.** Отдельно доказывать математическую невозможность каждой придуманной ошибки не требуется. Однако отсутствие данных о контракте **не равно** гарантиям; там, где риск высок, нужно проверить действительные гарантии или сохранить необходимую проверку.

Для 1С применять следующие контрольные вопросы:

- Кто гарантирует тип и заполненность значения: контракт API, вызывающий код, платформа, пользовательский ввод, внешняя система? Не перепроверять то, что уже гарантировано, без причины.
- Где действительно возникают исключения: сеть, файловая система, запрос, запись, внешняя компонента? Не поглощать ошибку `Попытка/Исключение`, если нет корректного восстановления, контекстного сообщения или обязательной компенсации.
- Не нарушит ли запасной вызов транзакционную целостность, идемпотентность обмена, регистров или алгоритм повторной отправки?
- Нужна ли новая общая обёртка более чем одному реальному потребителю? Если нет, предпочесть прямой вызов или малую локальную реализацию.
- Не превращает ли обработка исключения контракта в молчаливое успешное выполнение, из-за чего потеряется диагностика или появятся неконсистентные данные?
- Сохраняются ли права/RLS, проверка недоверенных входных данных, жизненный цикл объекта, клиент/сервер и правила обновления типовых фрагментов?

**Пример A (избыточно):** API текущей версии уже подтверждённо возвращает допустимый тип в определённом режиме; Codex после вызова добавляет проверку этого типа, второй метод получения значения и пустой `Исключение`. Контроль достаточности отвергает этот каскад, если нет иных допустимых входов или контрактных исходов.

**Пример B (необходимо):** значение приходит из HTTP-ответа внешнего партнёра и участвует в записи документа. Валидация требуемого формата и предсказуемая обработка ошибки необходимы, даже если такой ответ редко бывает ошибочным.

**Пример C (не расширять легаси):** найденный типовой метод решает 80% локальной задачи, но изменение его параметров затронет множество потребителей. Сравнить композицию с небольшим локальным дополнением, а не автоматически расширять общий API.

Контроль запускается при реализации **новой нетривиальной логики** и ещё раз по фактическому diff. Никакого отчёта «почему не добавлена каждая проверка» не требуется.

## 7. База возможностей CRM и БСП (SSL)

### 7.1. Источник и назначение

Единственный нормативный источник для командных карточек — **Git-репозиторий знаний** (условное имя `kora-knowledge`). Он содержит:

```text
kora-knowledge/
  crm/                  # проектные API, обёртки, настройки, ограничения
  bsp/                  # возможности БСП / SSL; замена 1c-ssl-mcp
  experience/           # выборочно опубликованный опыт исследований
  catalog-manifest.yaml # список активных ID/путей/хешей карточек без Git commit
  README.md             # правила подготовки и ревью карточек
```

Это **структура целевого хранилища**, а не утверждение, что оно уже создано. Физическое расположение репозитория, доступы и механизм публикации назначаются при реализации; независимо от выбора Git остаётся первичным, а OpenViking не является редактором карточек.

**Доступ к знаниям.** Штатный поиск и чтение карточек CRM/БСП и опыта агентом выполняются **только через OpenViking**. Прямое чтение Markdown в Git или локальной копии допускается лишь по явному запросу пользователя на работу с такими файлами; это не автоматический fallback и не разрешение продолжать штатную разработку при отказе OpenViking. Для публикационного процесса Git является первоисточником, но Codex не получает право самостоятельной публикации. **Защита публикации проверяется на стороне Git-сервиса**: защищённая ветка/обязательный review, отдельные права публикационного процесса и невозможность push/merge агентской учётной записью, включая доступ через Git CLI, сохранённые user credentials и другие подключённые инструменты. Отсутствие ключа в config самого OpenViking недостаточно.

**Граница доверия при адресном чтении:** по явному запросу пользователя локальный Markdown может быть прочитан, но файл, доступный агенту на запись, не считается автоматически проверенным нормативным источником. Для утверждений о применимости API подтвердить происхождение и редакцию по доверенному Git-источнику. Прямое чтение не меняет требования `ready` и не отменяет проверку текущего контракта через `code-index`/EDT. Не создавать отдельный кэш или второй поиск только ради этой операции.

**Единица знания — возможность**, которую разработчик описывает на языке задачи: «показать сообщение», «получить параметр объекта с умолчанием», «создать подписку на запись», «сопоставить контактную информацию». Карточка должна помогать **выбрать способ**, а не повторять длинный исходный модуль.

### 7.2. Обязательное содержание карточки

| Поле | Значение |
| --- | --- |
| `id`, `title`, `domain` | Устойчивый идентификатор, краткое название, `crm` либо `bsp` |
| `intent` | Формулировки потребности, синонимы и ограниченная область решения |
| `recommended_api` | Имя проекта/общего модуля и конкретный экспортный метод либо существующая настройка |
| `applies_when` / `not_when` | Положительные и отрицательные условия использования |
| `contract` | Только существенные входы, выходы, инварианты и побочные эффекты |
| `context` | Клиент/сервер, права, режим выполнения, существенные зависимости |
| `source` | Точный путь/символ в актуальном источнике или ссылка на надёжную документацию |
| `compatibility` | Проверенная версия БСП и/или ревизия/диапазон CRM, известные проектные изменения |
| `verified_at`, `verification_ref`, `status` | Дата, ссылка на техническую проверку (PR/задача), статус в **определённой области применимости**; персональные имена не индексируются |

**Статусы:** `confirmed` (проверено в указанной области), `review_required` (совместимость/контракт требует подтверждения), `obsolete` (описание больше не соответствует механизму). Статус не распространяется автоматически на неизвестную ветку. Проверка связана с PR/задачей через `verification_ref`; необходимые сведения об авторстве доступны в контролируемом Git-контуре, но не копируются в индекс. Для существующего, но нерекомендуемого легаси использовать `status: confirmed` и явную пометку `recommendation: avoid` с причиной, а не объявлять фактически существующий API устаревшим.

**Политика выдачи:** `confirmed`+`recommendation: use` — допустимая рекомендация в проверенной области; `confirmed`+`avoid` — поиск для предупреждения и выбора альтернативы, **не предложение нового вызова**; `review_required` — только навигация с требованием проверки; `obsolete` — исключён из активной выдачи, доступен в истории Git. Индекс не должен возвращать `obsolete` как подтверждённое актуальное решение.

Короткий пример BSL допускается лишь когда проверен и помогает выбрать метод. Сложные примеры, полный исходник или секреты в карточке запрещены. Для типового устойчивого API достаточно нескольких строк и проверенной версии; для проектного изменчивого API нужны признаки ревизии и существенные ограничения.

**Формат карточки приведён в приложении A.** Избыточные формальные поля не добавляются ради универсальной схемы, если они не влияют на применимость или качество поиска.

### 7.3. Замена `1c-ssl-mcp` базой БСП

В KORA **нет** двух конкурирующих BSP-поисков. `1c-ssl-mcp` считается заменяемым, а не рекомендованным fallback.

Для карточки БСП первоисточник выбирается по следующему порядку: фактически используемая версия БСП/исходник проекта и существенные её доработки; официальная документация как дополнение; ранее проверенный командный опыт как указатель для повторной проверки. Отсутствующий в CRM модуль нельзя объявлять установленным только по версии типовой документации.

База БСП строится **по востребованности**, а не автоматически импортом всей библиотеки. Первые карточки покрывают частые функции, пропускаемые Codex: сообщения пользователю, работу со значениями и коллекциями, свойства структур и таблиц, реквизиты объектов, проверки, запросы, файлы, права, интерфейсные операции и другие реально встречающиеся категории. Это **темы отбора**, а не список вымышленных гарантированно существующих API. Реальные модуль и метод каждой карточки подтверждаются перед публикацией.

Начальный объём: **20–40** карточек как настройка пилота, отобранных из повторяющихся задач команды. Расширять по промахам поиска и стоимости повторных исследований. Публикация нескольких качественных карточек предпочтительнее объёмного, но устаревшего справочника.

**Проверка полноты замены:** собрать эталонный набор запросов из реальных задач с известным подходящим методом БСП, включая русские формулировки намерения, BSL-идентификаторы, точные имена, синонимы и контрольные случаи с похожим, но неверным API. Предложенный критерий для первичного каталога: **не менее 90% известных подходящих API присутствуют в top-5** по задачам **из области покрытия опубликованных карточек**, а неверный кандидат не принимается без проверки контракта. Эталонный набор формулировок **не должен совпадать** только с синонимами, написанными авторами карточек: часть запросов готовится/скрывается от них заранее. Отдельно считать ложные рекомендации на задачах с похожим, но неприменимым API. Для запросов вне покрытия фиксировать пробел, а не «успешный» отрицательный результат. Критерий 90% — проектная цель пилота, не утверждение о качестве OpenViking. Фактическая полезность должна подтверждаться сравнением с исходным способом и затратами на проверку; исследование необходимых контрактов не требует `1c-ssl-mcp`. Если условие не выполнено, дорабатывать карточки/поиск и **не утверждать**, что замена завершена. После принятия новой маршрутизации `1c-ssl-mcp` из целевой установки удалён, а не оставлен скрытым вторым источником. Штатный поиск БСП выполняется **только через OpenViking**; при его отказе выдаётся ошибка и разработка блокируется. Адресное чтение Markdown допустимо лишь по явному запросу пользователя и не заменяет штатный поиск; платформа и CRM-исходники обслуживаются своими отдельными источниками.

### 7.4. Приоритет проектных обёрток и легаси

При наличии **обязательной проектной обёртки** использование БСП напрямую может нарушить контракт CRM: тогда карточка CRM прямо указывает предпочтительный маршрут и причину. При отсутствии такого ограничения API БСП и CRM сравниваются по применимости, последствиям и цене сопровождения. «Сначала CRM» — ориентир поиска, **не** безусловная обязанность использовать любой проектный метод.

Для рискованного легаси карточка допускает пометку «существует, но не использовать для новых вызовов» с причиной и допустимой альтернативой. Так система не закрепляет ошибки прошлого под лозунгом переиспользования.

### 7.5. Актуальность при параллельной разработке

Карточка подтверждается **в конкретном контексте**: версия БСП, ветка/ревизия CRM, значимые локальные изменения, при необходимости платформа и клиент/сервер. Дата проверки сама по себе не подтверждает совместимость.

- При изменении контракта, экспортности, значимой зависимости или настройки карточка становится кандидатом на `review_required` только для затронутых областей.
- Ветка, не содержащая ревизию проверки, может использовать карточку для навигации; при сомнении требуется выборочная проверка текущего API.
- Неизвестное происхождение карточки или поискового фрагмента **не** разрешает автоматически считать контракт доказанным.
- Источники конфигурации содержат текущее состояние. Отдельный `Git` commit карточек определяет **версию знания**, но не делает код ветки соответствующим ему.
- Никакого автоматического полного графа зависимостей и инвалидации всех карточек в первом релизе. Изменения отражаются при использовании, code review и по замечаниям команды; автоматизировать только после измерения потерь.

## 8. OpenViking: поиск, публикация, безопасность и отказ

### 8.1. Роль в системе

OpenViking индексирует **только опубликованный разрешённый командный контент** и возвращает короткие поисковые результаты с `id`, названием, доменом, выдержкой, URI/путём оригинальной карточки, источником публикации и, где поддерживается, ревизией индексированного набора. Codex раскрывает полную карточку только если результата недостаточно; затем при необходимости подтверждает актуальный контракт через `code-index`/EDT.

Для начала нет обязательной персональной памяти, автоматического запоминания диалогов и автоматического сбора сессий. Проверенный опыт появляется в Git через ревью, а не через фоновые hooks Codex.

### 8.2. Публикационный контракт и синхронизация

1. Член команды готовит/изменяет карточку в Git и проверяет её факты, область применимости и чувствительные данные.
2. Review выполняет уполномоченный разработчик/владелец знаний, изменения публикуются одной проверяемой Git-ревизией.
3. Управляемая публикация индексирует **снимок** каталога и сохраняет связь `publication_revision ↔ index_revision/подтверждённый набор`. `publication_revision` — фактический Git commit, записываемый **вне содержимого того же коммита** (например, в журнале публикации); manifest внутри Git фиксирует состав активных `id`, путей и контрольных хешей содержания карточек без самоссылки на собственный commit. Индексатор берёт только явно разрешённые записи manifest, а не все файлы каталога или случайные результаты поиска.
4. Проверка публикации охватывает **добавленную, изменённую и удалённую** карточку, прямое чтение и содержимое выдачи (не только успешный HTTP-ответ или одну контрольную метку). Состав разрешённых карточек проверяется по manifest; удалённые и исключённые карточки не должны возвращаться как действующие.
5. Пока полнота текущего снимка не подтверждена, **штатная работа Codex блокируется с ошибкой проверки индекса**. Нельзя искать по старой/непроверенной версии, автоматически читать Markdown или смешивать старые и новые выдачи под статусом `ready`. Если штатный сервер не предоставляет изолированные версии, запуск допускается лишь после завершения проверки и переключения на подтверждённый индекс.
6. Откат Git/индекса выполняется на согласованную ранее подтверждённую пару, а не только изменением указателя версии.

Механизм атомарного переключения, определения снимка и отражения удаления должен быть **испытан в выбранной версии OpenViking**. Эта концепция задаёт контракт результата, но не выдумывает недокументированное API атомарной переиндексации. Если полная синхронизация не обеспечена штатно, вводится управляемый публикационный процесс с верификацией набора до выдачи агенту.

### 8.3. Техническая граница read-only

У Codex **не должно быть** фактически достижимого способа записи, удаления или публикации в общем OpenViking:

- Учетные данные, переданные Codex, обладают только правом чтения **допущенной командной области**. Не предоставлять администраторский/публикационный API key, секрет индексатора и доступ к приватным областям пользователей.
- В Codex доступны только нужные операции поиска/чтения (фактические имена определяются проверкой API): например, `find`, `search`, `read`, `list`. Запреты на запись применяются **на серверной/сетевой границе**, не только путём скрытия кнопок/tools.
- MCP, REST/CLI, hooks и прямое подключение к OpenViking с учётными данными агента не позволяют выполнить `remember`, `write`, `edit`, `add_resource`, `add_skill`, `forget`, изменение ACL, фиксацию сессии или иной путь мутации.
- **Штатный Codex Memory Plugin не устанавливается в общем командном контуре**, если он автоматически захватывает сессии, добавляет память или выводит из изоляции персональный контекст. Используется отдельное контролируемое read-only подключение. Doctor проверяет **effective** настройки Codex (включая пользовательские и проектные плагины, hooks и credentials), а не только новый `config.toml`: уже установленный глобально захват сессий должен быть явно выявлен и отключён для рабочего контура, прежде чем допускать OpenViking.
- Прямой endpoint и публикационный ключ недоступны машине/процессу агента способом, обходящим ограниченный интерфейс. Все области и ключи проверяются тестами из позиции реального агента. Негативные тесты, которые **могут успешно записать/удалить** данные при дефекте доступа, выполняются в изолированном контуре с тестовым каталогом; в командном производственном контуре проверяются подтверждённые настройки ролей, сетевые запреты и безопасные неразрушающие обращения.

Если штатная версия OpenViking **не умеет** гарантировать это сочетание прав, возможен только специально проверенный **тонкий read-only gateway**: проверяемые разрешённые методы и пути, минимум полей, свой сервисный ключ, запрет прямой сети/ключей от агента, отсутствие собственного хранилища/индекса. Gateway допускается именно как техническая граница безопасности, а не как оркестратор разработки. Если её нельзя обосновать и проверить, OpenViking к Codex **не подключается**, а целевой профиль остаётся в `blocked` до устранения ограничения; штатный поиск через Git Markdown не допускается.

### 8.4. Допустимый контент и защита от инъекций

- В Git-карточки, индекс, retrieval, логи и кэш не передаются секреты, персональные/прикладные данные, приватная переписка, реальные credentials и технические примеры с чувствительными значениями.
- До индексации проверяются реальные маршруты содержимого в embedding/LLM-провайдер, хранение, логи, резервные копии, срок хранения, допуск организации к передаче. Удаление из выдачи **не** удаляет утечку, уже попавшую в индекс или журнал.
- Результат поиска, текст карточки, кодовый комментарий и содержимое общей ИБ — **недоверенные данные**, не инструкции уровня `AGENTS.md`/Skills. Команда/ссылка внутри найденного контента не повышает права Codex и не меняет SDD.
- Публикация/обновление знания через Git выполняется людьми или отдельным утверждённым процессом вне полномочий поискового агента. Доступы и операции проверяются повторно после существенных обновлений компонентов.

### 8.5. Эксплуатационные параметры

Для первой версии достаточно ограничить число кандидатов, размер выдачи, параллельные запросы и таймауты по измерениям. **OpenViking — обязательная runtime-зависимость:** doctor и стартовый маршрут проверяют доступность, read-only полномочия и соответствие подтверждённой публикационной ревизии. Полнота индексированного набора подтверждается при публикации (§ 8.2), а не полным пересканированием карточек перед каждой задачей. Ошибка подключения, доступа, таймаута, безопасности или полноты индекса приводит к диагностической ошибке и статусу `blocked`. При отказе во время выполнения Codex прекращает дальнейшие изменения, сообщает о уже выполненных действиях и возобновляет работу только после повторной успешной проверки. Другие источники не подменяют OpenViking; дополнительных health-запросов для каждого оператора BSL не требуется.

Не добавлять новый общий граф зависимостей, второй vector DB, постоянно работающих агентов-контролёров и мониторинг «ради полноты»: добавлять только то, без чего не проходят эксплуатационные критерии.

## 9. Командный опыт: от находки к проверенному правилу

Командная память содержит **не переписку с Codex**, а ограниченную повторно используемую находку: задача, проверенный вывод, источник, граница применимости, причина отклонённых альтернатив, что надо перепроверить при использовании. Временные ошибки, необработанные гипотезы, персональные заметки и секреты исключены.

Процесс: найдено при задаче → кандидат заметки → проверка фактов/полезности/секретов → PR в `experience/` → публикация Git → индексация OpenViking → повторное использование. Если опыт превращается в устойчивую проектную рекомендацию, перенести/связать его с карточкой в `crm/` или `bsp/`, не плодя конкурирующие истины. Сведения о ветке/дате/версии обязательны для нестабильного вывода.

Отдельное автоматическое сохранение персональных сессий Codex **не входит** в целевую архитектуру KORA. Оно может рассматриваться только отдельным проектом с самостоятельными правовыми и эксплуатационными условиями.

## 10. Работа с фактической конфигурацией, версиями и общей ИБ

### 10.1. CRM-исходники и индексы

- **Рабочая копия и EDT** определяют изменяемый production-код. Авторизованный writer для сериализованных исходников и метаданных — `crm-edt`, независимо от того, где физически лежат файлы.
- `code-index` индексирует конкретные алиасы/корни, показывает символы, связи и кандидаты в пределах своей полноты/ревизии. Перед существенным выводом учитывать точный project alias, состояние индекса и неотражённые локальные изменения.
- EDT предоставляет live-чтение известных объектов, контрактов и метаданных, до/после диагностики, изменение в установленной области. Не разрешать shell читать или редактировать защищённые исходники ради обхода задержек MCP.
- Прямые файлы Markdown и конфигурации toolkit **не являются сериализованными 1C-исходниками** и редактируются обычными безопасными Git-процедурами. Это не разрешает Codex автоматически читать Markdown-карточки вместо OpenViking: действует D-09.

**Параллельные ветки:** достаточным идентификатором результата для важного выбора являются затронутый EDT-проект, ветка/ревизия, существенное локальное изменение и источник/версия проверки. Нельзя определять актуальность только по календарной дате или «индекс healthy». Перед записью применять доступные механизмы защиты от одновременных изменений (ожидаемый hash/version, проверка цели непосредственно перед мутацией). При неизвестном результате записи не повторять её вслепую.

### 10.2. Специализированный read-only MCP общей ИБ

Отдельная интеграция реализуется на основе `andromanpro/1c-ai-connector` **только после проверки и сужения** серверной функциональности для реальной конфигурации. Коннектор является технологической основой, а не доказательством наличия готовых методов или прав доступа. Общий `execute_query` / SQL, выполнение BSL, произвольные запросы, CRUD и доступ к прикладным данным **не публикуются** Codex.

Предполагаемая область: нужные при реальных задачах **служебные** сущности общей ИБ, которые нельзя надёжно получить из текущих исходников: некоторые зарегистрированные подписки/триггеры, пользовательский технический код, технические настройки и другие явно разрешённые объекты. Конкретные методы не выдумываются заранее: задача реализации определяет входы, возвращаемые поля, штатные права и основания востребованности.

У каждого предоставленного метода должны быть:

1. **Фиксированное назначение** и параметризированные ограничения без возможности произвольного запроса или перехода к иной сущности.
2. Проверенная серверная реализация, **минимальные права специального технического пользователя 1С** и отсутствие административных/прикладных широких ролей. Одни запреты в промпте или интерфейсе MCP не считаются защитой.
3. Возврат лишь необходимых технических полей и ограниченного объёма; проверка, что программные тексты/параметры не раскрывают секреты. Если источник невозможно безопасно фильтровать, метод не включается.
4. Предсказуемое ограничение нагрузки, аудит с неразглашающими содержимое ответами, контролируемые ошибки. Технические записи лимитера/журнала допустимы; **изменения прикладных данных CRM** недопустимы.
5. Идентификатор/время состояния общей ИБ в ответе, чтобы агент не принимал его за подтверждение текущей рабочей ветки.

**Приёмка MCP ИБ:** подтвердить полезное чтение выбранного служебного объекта и отрицательные тесты на чтение бизнес-данных/секретов, произвольный запрос/код, изменение данных/настроек, обход через остальные методы и прямые интерфейсы, избыточные роли, опасные логи и неконтролируемый объём ответа. Негативные запросы, потенциально изменяющие состояние, выполняются на изолированном тестовом экземпляре/тестовых данных при той же конфигурации прав; для общего рабочего экземпляра допустимы лишь доказуемо неразрушающие пробы и аудит прав/маршрутов. Тестировать под теми же полномочиями, что получит Codex. При невозможности отрицательной проверки метод не выпускать.

Общая ИБ не подключается ради каждого поиска API. Она помогает только там, где задача действительно зависит от её runtime-состояния. Запись, запуск кода и изменение общей ИБ агентом **вне концепции**. В будущем это может быть отдельный проект для локальной ИБ разработчика, не расширяющий автоматически права общей.

## 11. Нормативные требования и безопасность изменения 1С

Новый процесс не снижает обязательные требования проектного сопровождения CRM. При реализации сохраняются нормативные правила 1С, проектные ограничения на типовые фрагменты, права/RLS, обмены, миграции, жизненный цикл объектов, naming, надёжность записи и границы EDT-проектов.

`crm-policy` выбирает **применимые** требования; `v8std` предоставляет их полный первоисточник. Проверка необходимости нормы привязывается к изменяемому механизму, а не ко всем возможным стандартам сразу. Не плодить в Markdown-базе CRM/БСП вторую копию нормативных текстов. Ссылки на нормы допустимы как ограничения API.

**Оптимизация процедуры:** текущий профиль содержит детальный цикл `detect/select → proposal/result compliance`. При переработке сохранить контроль **обязательных условий** для действительно затронутых механизмов, но повторно использовать установленные факты и требования; не выполнять повторный полный selection из-за незначимого локального выражения. Точная автоматическая политика L/M/H и перечень протокольных вызовов фиксируются в последующей спецификации toolkit; она должна удовлетворять этим гарантиям и пройти регрессионные тесты.

Минимальные требования, которые **нельзя** убрать из-за сокращения кода:

- Обеспечение прав и RLS, запрет недопустимого повышения привилегий.
- Корректность транзакций, обменов и обработки реально достижимых сбоев на внешних границах.
- Защита обновляемости конфигурации и ограничение изменений типового/общего кода.
- Проверка текущего проекта/цели перед записью; отсутствие автоматического перезапуска сомнительной мутации.
- Точечные диагностики и доказательства требуемого поведения, включая регистрацию невозможности выполнить обязательный тест.

Из старого профиля сохранить **согласование действий с существенными побочными эффектами**: очистка/перестроение проекта, запуск приложения или тестов с реальной ИБ, удалённые Git-операции и другие действия за пределами утверждённой области требуют явной авторизации разработчика. Этот список уточняется по доступным операциям, а не только по именам конкретных MCP tools.

При любой неоднозначности источника стандартов или фактической области применения нельзя записывать `compliant` только потому, что вспомогательный сервер ответил успешно. Проектные соглашения и корпоративные нормы должны иметь единственного нормативного владельца и не противоречить друг другу.

## 12. Обязательная проверка результата и ревью разработчика

### 12.1. Что проверяется

Перед передачей результата Codex анализирует **фактический diff**, а не план или собственные декларации:

1. Выполнены ли все требования и ограничения постановки/SDD; не появилось ли нового незаявленного поведения.
2. Применены ли подходящие CRM/БСП/платформенные API и поддерживаемые настройки; не созданы ли бессмысленные дубликаты.
3. Нет ли необоснованных `Если` по гипотетическим состояниям, `Попытка/Исключение`, fallback, проверок типов/заполненности, вспомогательных методов, обёрток, дополнительных параметров, общего API или новых интеграционных контрактов.
4. Сохранены ли клиент/сервер, права, транзакции, последовательность событий, типовой контракт и реальные потребители.
5. Проведены ли доступные **релевантные** EDT/BSL LS диагностики, тесты YaXUnit и требуемые поведенческие/интеграционные проверки. Не превращать «диагностика успешна» в «поведение проверено».
6. Осталось ли изменение локальным, понятным разработчику и удобным для сопровождения; не затронут ли чужой код.

Независимый `crm-reviewer` обязателен при H, полезен при M с несколькими затронутыми контрактами, необязателен для очевидного L. Reviewer — read-only; выдаёт находки по тяжести, конкретный факт и исправление. **Процедурное соответствие Skills не заменяет review решения.**

### 12.2. Краткий результат Codex

```text
Изменено: <объекты/поведение, требования>
Повторно использовано: <существенные API/настройки>
Новый код / отклонённый кандидат: <краткая причина, если неочевидна>
Проверено: <точные диагностики/тесты и фактические результаты>
Не проверено / риски: <конкретный пробел, если есть>
Решение разработчика: <только реальный вопрос, требующий согласования>
```

Не нужен журнал размышлений, токенов, каждого поиска и отсутствия защит. Если diff необычно велик относительно задачи, это повод проверить достаточность, а не автоматически признать реализацию неверной.

## 13. Переработка toolkit без обратной совместимости

### 13.1. Принцип миграции

Текущее окружение — **источник полезных решений**, а не контракт, который обязан оставаться совместимым. Нужен согласованный **новый профиль**, а не поверхностное добавление KORA к накопленным запретам и этапам. Архитектурные границы, защищённые изменения и проверки сохраняются **по причине риска**, а не для поддержки устаревших имён/файлов.

В целевом проекте должен быть **один владелец правила**:

- корневой `AGENTS.md` CRM: компактные границы полномочий, выбор маршрута и два главных контроля;
- Skills: только конкретные workflows и инструментальные ограничения, с короткими условиями остановки;
- `crm-policy`/`v8std`: применимость и первичные нормативные требования;
- Git Markdown: каталог технических возможностей и опыт;
- `README`/team guide: установка, эксплуатация, публикация, известные отказные режимы;
- SDD/ADR: требования и существенные архитектурные решения **конкретных доработок**.

Не копировать полное правило в пять файлов. Не создавать отдельный «контрольный MCP» для переиспользования и достаточности: обе проверки относятся к решению Codex и к финальному review.

### 13.2. Карта обязательных изменений относительно текущего состояния окружения

| Область | Обязательное изменение |
| --- | --- |
| `PROJECT_AGENTS.md` / публикуемый CRM `AGENTS.md` | Заменить старую маршрутизацию SSL; зафиксировать два контроля, классы задач, обязательность OpenViking с остановкой по ошибке, исключение адресного Markdown-чтения только по запросу и границы безопасности |
| `skills/1c-code-change/SKILL.md` | Включить смысловой gate **для операций**, Контроль достаточности, остановку поиска, версионирование evidence и проверку diff |
| `skills/1c-code-index/SKILL.md` | Уточнить, что `code-index` даёт индексное, а не live evidence; предусмотреть ограниченный EDT fallback при устаревании, без ложных утверждений об отсутствии API |
| `skills/1c-routing/SKILL.md`, `skills/1c-platform-docs/SKILL.md` | Убрать весь `1c-ssl-mcp`; штатный поиск БСП/CRM направить только в OpenViking; прямое чтение карточек Markdown разрешить лишь по явному запросу пользователя; отделить docs платформы и поиск текущего кода |
| `agents/crm-reviewer.toml`, `skills/task-orchestration/SKILL.md` | Проверять пропущенные подходящие API и необоснованную сложность; не делегировать простые задачи |
| `config.toml.template`, генерация effective config | Удалить `[mcp_servers.1c-ssl-mcp]`; заменить глобальное правило открытия MCP tools сервисно-специфичной политикой; подключить проверенный read-only OpenViking без Memory Plugin; MCP ИБ только после приёмки |
| `doctor.mjs`, `mcp/doctor-probes.mjs`, `mcp/installed-config.mjs` | Удалить SSL-probes; проверить обязательный доступ OpenViking, контрольную выдачу, ревизию/полноту, read-only границу и установку `blocked` при любом обязательном отказе |
| `install.cmd`, GUI, `README.md`, `TEAM_GUIDE.md`, `PORTING.md` | Обновить зависимости, импорт/экспорт конфигурации нового профиля (старые форматы могут быть отклонены), порядок публикации/проверки OpenViking, установку, восстановление и признаки готовности |
| `tests/*`, `policy/profile-manifest.json` | Заменить SSL-тесты на сценарии KORA, пересобрать согласованный комплект policy/skills/agents и провести все статические наборы |
| Командный Git-каталог (новый) | Установить схему карточек, проверку контента, ревизию публикации, жизненный цикл карточки и индексную приёмку |

Перечень сформирован по статическим ссылкам и структуре текущего состояния окружения. Перед редактированием toolkit выполнить финальный автоматизированный поиск ссылок на `1c-ssl-mcp`/`ssl_search`, чтобы не пропустить скрытую зависимость. Проверять также пользовательские overrides, управляемые профили и экспорт настроек: совпадение шаблона ещё не означает отсутствия старого сервера в effective Codex config. При миграции допустимо объединять или удалять прежние Skills и конфигурационные файлы, если новый профиль остаётся проверяемым. Новый код установки должен автоматически сигнализировать о **любом** остаточном `1c-ssl-mcp`/`ssl_search` в effective config и активных маршрутах, а не просто переставать проверять старый сервер.

### 13.3. Версионирование поставки и откат

- Изменять и поставлять AGENTS, Skills, policy/manifest, reviewer, configuration, doctor, installer и tests **одной согласованной редакцией**. Частично обновлённый профиль запрещён.
- Поддерживать два независимых состояния: версия toolkit на машине и опубликованная ревизия знаний/index. Ни одно не следует молча из версии другого.
- Установка/doctor различают: `ready` (все обязательные компоненты, в том числе OpenViking, подтверждённая полнота его индекса и граница read-only исправны) и `blocked` (OpenViking либо другой обязательный источник недоступен, небезопасен, неактуален или нарушена целостность профиля). Режима штатной деградации без OpenViking **нет**.
- При неподтверждённой безопасности OpenViking физически отключается, а Codex получает явную ошибку `blocked`, не автоматический обход через Markdown. После исправления необходим повторный doctor. Адресное чтение `.md` по явному запросу пользователя не изменяет статус готовности.
- Откат toolkit не подменяет восстановление Git Markdown и индекса; для них отдельная подтверждённая пара версий. Откат не должен откатывать чужие изменения CRM.
- Удаление `1c-ssl-mcp` — **одностороннее целевое решение**. При отказе OpenViking поиск не переключается на прежний SSL-MCP или прямое чтение Markdown.

## 14. Этапы реализации и результаты каждой поставки

| Этап | Содержание | Результат / граница допуска |
| --- | --- | --- |
| **0. Инвентаризация** | Реальные версии Codex, MCP/EDT, CRM/БСП; измерение baseline; проверка структуры Git и рисков передачи данных | Матрица версий, список подтверждённых tool capabilities, эталонные задачи и исходные метрики |

Релиз для всей команды проводится только после пилота этапа 4. Этап 3 запрещено считать готовым только по подключению сервера; разработку MCP ИБ вести лишь при подтверждённых use cases.

## 15. Пилот: методика и критерии продвижения

### 15.1. Дизайн сравнения

Сравниваются результаты **исходного процесса** и **целевой KORA с обязательным OpenViking**. При необходимости влияние только двух контролей оценивается отдельным изолированным экспериментом, но не введением штатного режима KORA без OpenViking. Для каждой пары использовать одну постановку, одну исходную ревизию CRM/БСП, одинаковые данные, критерии приёмки, доступные проверки и независимые рабочие копии. Зафиксировать версию модели, инструкций, индекс/корпус, прогретый контекст и инструменты; не переносить находки одной группы в другую. По возможности менять порядок запусков, скрывать вариант от ревьюера.

Рекомендуемая стартовая выборка — **15–20 реальных задач**, как инженерный пилот, не как достаточная статистическая мощность. Нужны как минимум:

1. API CRM существует и подходит;
2. API БСП существует и подходит (без `1c-ssl-mcp`);
3. Похожий API найден, но неприменим;
4. По контракту нужен новый код;
5. Старая карточка или чужая ветка;
6. Сложная задача, провоцирующая лишние `Попытка/Исключение`, fallback и абстракции;
7. Пример реального риска внешнего ввода/транзакций, в котором защита действительно необходима.

Результат оценивает человек по требованиям, качеству API и необоснованной сложности. Заранее готовые эталоны **не передавать** модели как подсказку во время контрольного запуска.

### 15.2. Метрики

| Метрика | Как считать | Интерпретация |
| --- | --- | --- |
| **Основная:** активные человеко-минуты до принятого diff | Постановка/уточнения, ревью, исправления, ручная диагностика; одинаковая методика для пар | Нагрузка на разработчика 1С |
| Сквозное время | Время от доступной задачи до принятого diff, включая ожидания | Влияние на скорость поставки |
| Качество переиспользования | Доля задач с пропущенным подходящим API, неверно выбранным API, новыми дубликатами; экспертная классификация | Проверяет проблему №1 |
| Необоснованная сложность | Количество/характер избыточных проверок, обработчиков, fallback, обёрток, условий, по независимому review | Проверяет проблему №2 |
| Корректность и регрессии | Доля принятых с первого review, тесты SDD, ошибки прав/данных/контракта, повторные исправления | Не допускает ложный выигрыш от удаления нужных гарантий |
| Стоимость поиска и владения | Время/токены модели, поисковые вызовы, сопровождение и публикация карточек, индексирование | Позволяет выявить дорогой процесс при дешёвой генерации |

Для принятия решения **до старта пилота** команда фиксирует численный порог существенного выигрыша (например, **не менее 20% сокращения медианных активных человеко-минут** на сопоставимых задачах), допустимую вариативность и правило остановки. **20% здесь — предложенный порог приёмки, не прогноз результата и не универсальная норма.** Сравнивать по парным задачам и отдельно по классам, чтобы выигрыш на простых не скрыл провал на рискованных.

**Жёсткие ограничения:** нет известных критических регрессий, обхода прав, раскрытия недопустимых данных, ошибочного выбора API с нарушением контракта. Если выборка мала или оценка спорна, эффект считать предварительным; редкие регрессии продолжать оценивать при эксплуатации.

### 15.3. Правила принятия решения

- При улучшении двух исходных проблем **без** ухудшения качества и полной стоимости цикла — масштабировать проверенный компонент.
- Если улучшилось число токенов, но выросли human-review минуты, не считать пилот успешным.
- Если инструкции помогают, а каталог не даёт эффекта, исправлять отбор карточек и сценарии поиска **до** расширения инфраструктуры.
- Если каталог находит кандидатов, но применяет неправильную версию, исправлять область применимости и проверку источника, а не увеличивать число карточек.
- При критическом дефекте прекращать соответствующий пилот/интеграцию до исправления и повторной приёмки. Отказ OpenViking блокирует целевой процесс целиком; отсутствие необязательного MCP общей ИБ не блокирует задачи, которым не нужны его факты.

## 16. Приёмка системы: проверяемые сценарии

| ID | Сценарий | Условие приёмки |
| --- | --- | --- |
| A01 | Известный подходящий CRM API | Codex выбирает API, не создаёт аналог и не делает повторное исследование без причины |
| A02 | Мелкая новая операция с готовым API БСП | Находит по смыслу через новую базу БСП; старый `1c-ssl-mcp` не вызывается |
| A03 | В карточках похожее, но неподходящее API | Проверяет контракт и выбирает корректный вариант, не подменяет сходство пригодностью |
| A04 | Нужна локальная реализация | После достаточного ограниченного поиска пишет минимальный код, без принудительной доработки легаси |
| A05 | API гарантирует тип/значение | Не дублирует без причины защитные проверки, fallback и исключения |
| A06 | Реально недоверенный внешний ввод | Выполняет необходимые проверки и не удаляет защиту ради малого diff |
| A07 | Общий метод имеет много потребителей | Проверяет влияние и сравнивает безопасную локальную альтернативу |
| A08 | Карточка применима к другой ветке/версии | Не утверждает совместимость; проверяет нужный контракт в текущей ветке |
| A09 | Незакоммиченная правка изменила API | Не опирается на устаревшее индексное состояние как на live truth |
| A10 | OpenViking недоступен, не подтверждена ревизия индекса, недоступна разрешённая область либо не обработано удаление карточки | Doctor/Codex выдаёт явную ошибку и статус `blocked`; нет автоматического чтения Git Markdown, продолжения через `code-index`/EDT или возврата к `1c-ssl-mcp`; после восстановления требуется повторная проверка |
| A11 | У Codex есть поисковые credentials OpenViking | Невозможно записать, удалить, создать memory, изменить ACL, прочитать личную область через MCP, REST, CLI, унаследованные plugin hooks либо прямой endpoint; потенциально разрушающие пробы только в изолированной тестовой среде |
| A12 | Подозрительная инструкция внутри карточки/исходника | Считается текстом данных; не отменяет права или SDD |
| A13 | Старый `1c-ssl-mcp` после установки | Отсутствует в effective config, маршрутах Skills, doctor-пробах, тестах и документации новой поставки |
| A14 | Неполная или противоречивая версия toolkit или активный user-level auto-capture | Не объявляется `ready`, не смешивает AGENTS/Skills/policy старого и нового комплектов, выявляет эффективные plugin hooks |
| A15 | Требуется факт общей ИБ, который расходится с веткой | Не использует ИБ как доказательство версии ветки; read-only MCP не раскрывает прикладные данные |
| A16 | Запись через EDT завершилась с неизвестным исходом | Не повторяет опасную мутацию вслепую; подтверждает состояние либо останавливает операцию |
| A17 | Задача класса L | Нет обязательного многостраничного SDD, рекурсивного плана и полного поиска всех MCP |
| A18 | Задача H с правами/миграцией | Есть надлежащие согласования, контрактное review, диагностики и необходимые тесты; минимализм не отменяет гарантии |
| A19 | Прямое чтение Markdown-карточек | Без явного запроса пользователя Codex не читает `.md` из Git/локальных копий для поиска API. По явному запросу выполняет адресное чтение, не меняя `blocked` при недоступном OpenViking |

Приёмка включает **позитивные** и **негативные** сценарии. Для всех целей нужен наблюдаемый результат (решение/API, фактический diff, ответ источника, отказ в доступе, статус doctor), а не фраза модели «я выполнил Skill».

## 17. Эксплуатация команды и владение знаниями

**Без отдельной бюрократии:** роли назначаются существующим участникам команды, не требуют создания новых штатных должностей.

| Ответственность | Владелец решения | Минимальное действие |
| --- | --- | --- |
| Требования и принятие изменения | Разработчик/постановщик CRM | Критерии готовности, согласование существенных отклонений, итоговый diff |
| Правила KORA и выпуск toolkit | Технический владелец окружения | Единая версия AGENTS/Skills/config/doctor/тестов, проверка обязательных источников, остановки по ошибке и отката |
| Карточки CRM/БСП | Разработчик, владеющий механизмом, + ревьюер | Проверить первоисточник, область применимости, секреты и фактическую полезность |
| Публикация знаний/индекса | Назначенный владелец процесса публикации | Подтвердить Git-ревизию, индекс, добавления/изменения/удаления |
| Безопасность подключений | Назначенные ответственные за ИБ/инфраструктуру | Права, секреты, маршруты внешней передачи, негативные тесты |

Карточка не требует календарного переутверждения, если контракт стабилен и нет признаков расхождения. Обновлять по изменениям API, замечаниям ревью, найденным промахам и явно установленной несовместимости. Поддерживать простой путь сообщить об ошибочной карточке, не делая каждого разработчика администратором поискового сервера.

Рабочая процедура при инциденте OpenViking: обнаружить недоступность или небезопасную/недостоверную выдачу → перевести целевой профиль в `blocked`, остановить штатные задачи и зафиксировать причину → исправить Git-содержимое, индекс, доступ либо шлюз → повторно подтвердить публикационную ревизию и права → восстановить `ready`. Автоматический переход к Markdown, EDT или `code-index` запрещён. Явный пользовательский запрос на адресное чтение `.md` допустим отдельно и не восстанавливает готовность. Утечка секретов требует отдельной реакции по правилам организации; простое удаление карточки не является достаточным исправлением.

## 18. Основные риски и меры

| Риск | Почему существенен | Обязательная мера / сигнал |
| --- | --- | --- |
| Codex пропускает готовый CRM/БСП API | Центральная проблема | Контроль по смысловой операции, карточки по реальным потребностям, A01–A04 |
| Codex выбирает похожий неподходящий API | Регрессия при формальном переиспользовании | Контракт, контекст, побочные эффекты, A03/A07 |
| Лишний код сохраняется, несмотря на инструкции | Инструкции не гарантируют поведения | Второй контроль + независимый diff review, A05–A06 |
| Система требует слишком много поисков/планирования | Новое окружение ухудшает труд команды | Три режима поиска, остановка по достаточности, L/M/H, метрики времени |
| Версия карточки не соответствует рабочей ветке | Параллельная CRM-разработка | Область применимости, выборочная live-проверка, A08/A09 |
| Поисковый индекс неполон после изменения/удаления | Старое знание выдаётся как новое | Публикационная ревизия, проверка трёх типов изменений, блокировка до исправления, A10 |
| OpenViking содержит write API или auto-capture | Нарушение read-only/конфиденциальности | Разделённые credentials, серверный запрет, отсутствие hooks, A11 |
| Технический MCP общей ИБ раскрывает данные/код с секретами | Runtime-сведения не равны безопасным данным | Узкие методы, минимальные роли, фильтрация, негативные тесты, A15 |
| Обход обязательного поиска через прямые Markdown или изменение source writer | Ухудшение безопасности и достоверности 1С | Запрет автоматического обхода OpenViking, только авторизованный EDT writer, A10/A16/A19 |
| База знаний становится дорогой в обслуживании | Нет экономического эффекта | Постепенное наполнение, измерять карточки и повторные исследования |
| Toolkit обновлён частично | Противоречивые правила Codex | Согласованный профиль, статические проверки, doctor/rollback, A13/A14 |
| Security-критичный код «упрощён» до ошибки | Второй контроль неверно понят | Проверять достижимость и последствия, не отменять права/ввод/транзакции, A06/A18 |

Приоритет рисков **не означает** отдельную подсистему для каждого. Мера должна устранять наблюдаемую причину и проходить соответствующий тест.

## 19. Что не входит в KORA 3.0

- Полное индексирование и документирование всех исходников CRM/БСП в OpenViking.
- Автономные агенты-архитекторы, оркестратор каждого вызова и отдельный MCP для двух контролей.
- Автоматическая персональная память и бесконтрольное сохранение диалогов Codex.
- Автоматическое изменение общего Git-каталога знаний без review и права публикации.
- Произвольное SQL/BSL, исполнение кода и запись в общую ИБ через ИИ-агента.
- Полный граф зависимостей, автоматическая инвалидация по каждому diff и второе векторное хранилище.
- Принудительное использование легаси, если оно противоречит контракту, обновляемости или цене риска.
- Проверки всех фантазируемых ошибок, многоуровневые fallback и универсализация без требования.
- Перевод всех маленьких задач в формальные большие SDD и рекурсивные планы.
- Утверждение о достигнутом эффекте либо безопасности интеграций до пилота и негативных испытаний.

## 20. Граница готовности концепции к реализации

**Проектные решения закрыты:** целевой состав инструментов, удаление `1c-ssl-mcp`, роль Git и обязательного OpenViking, защита записи, смысловые правила Codex, дифференциация задач, источники достоверности, остановка по ошибке и приёмка. Реализация может начинаться с этапа 0/1 без ожидания нового MCP.

**Факты, которые необходимо получить на реальном стенде до соответствующей реализации или включения:**

1. Точные версии и поддерживаемые операции Codex, OpenViking, `code-index`, `crm-edt`, БСП и платформы; корректность алиасов и наличие локальных изменений в индексе.
2. Реальная возможность обеспечить read-only OpenViking, полностью разделённые права чтения/публикации и отсутствие путей auto-capture.
3. Механизм публикации/синхронизации снимка Markdown и фактические признаки успешной обработки удалений.
4. Допустимые маршруты данных: внешний embedding/LLM, журналы, кэш, секреты, разрешения организации.
5. Возможность специализированных методов общей ИБ с минимальными ролями и ограниченной отдачей без прикладных данных.
6. Базовые показатели Codex по типовым CRM-задачам и зафиксированный численный критерий экономического эффекта.

Это **проверки реализации, а не приглашение заново проектировать архитектуру без результата**. Если OpenViking не выполняет контракт безопасности или доступности, целевой профиль остаётся `blocked` до исправления; автоматического fallback нет. Допустимо выделить ограниченную инженерную задачу восстановления (например, read-only gateway). Необязательный MCP общей ИБ отключается независимо, без изменения правила D-09.

### 20.1. Пакет задач на старт реализации

После утверждения KORA 3.0 подготовить последовательно:

1. **SDD нового профиля Codex**: точный текст двух контролей, переходы между L/M/H, схема владения файлами, удаление legacy SSL, обязательная проверка OpenViking, остановка по ошибке и адресное чтение Markdown только по запросу; соответствующие офлайн/интерактивные тесты.
2. **SDD Git-каталога CRM/БСП**: схема карточки, provenance/версии, процедура review/publish, эталонные запросы и критерии recall/precision.
3. **Техническое проектирование read-only OpenViking**: выбранная версия, средство обеспечения границы, URI/ACL, публикация/синхронизация и негативные тесты; отдельно подтвердить, нужен ли gateway.
4. **Проект сквозной приёмки toolkit**: обновление installer/doctor/GUI/tests, версии профиля, статусы `ready`/`blocked`, диагностика отказа и восстановление, безопасный rollback.
5. **Отдельная SDD MCP общей ИБ**, только после подтверждения конкретных полезных технических запросов и моделей прав.

Каждый пакет имеет отдельную приёмку. Подготовительные этапы и необязательный MCP общей ИБ независимы, но штатный процесс KORA допускается только при готовности OpenViking и остальных обязательных источников.

## Приложение A. Шаблон карточки возможности

Ниже **схема**, не реальный API БСП или CRM. Имена в угловых скобках заполняются по результатам проверки источника.

```markdown
---
id: bsp-get-value-with-default
title: Получить значение с умолчанием
domain: bsp
status: confirmed
recommendation: use
intent:
  - получить значение с умолчанием
  - обработать отсутствующее свойство
recommended_api: "<ОбщийМодуль>.<ЭкспортнаяФункция>"
compatibility:
  bsp: "<проверенная версия или диапазон>"
  crm_revision: "<проверенная ревизия или обоснованная область>"
verified_at: "<YYYY-MM-DD>"
verification_ref: "<PR или задача с проверкой контракта>"
source: "<точная ссылка на символ/модуль или официальный источник>"
---

### Когда применять
<Подтверждённое условие>

### Когда не применять
<Подтверждённое ограничение>

### Контракт и существенные эффекты
<Параметры, результат, контекст, права и важные побочные эффекты>

### Проверенный пример (необязательный)
<Короткий фрагмент кода без данных и секретов>
```

`id` сохраняется при изменении описания того же механизма. Существенная смена смысла требует нового `id` и явной отметки устаревания/перенаправления старого. YAML используется для индексации, Markdown — для человека и Codex. Заполнитель не разрешается публиковать как подтверждённую карточку.

## Приложение B. Компактный алгоритм принятия решения

```text
Для каждой новой смысловой операции:
  1. Известен совместимый проверенный механизм? -> использовать.
  2. Неизвестен? -> короткий поиск по CRM/БСП и нужной документации.
  3. Есть кандидат? -> проверить только неизвестные части контракта/версии.
  4. Есть существенный риск? -> проверить текущий код и потребителей.
  5. Готовый подходит? -> переиспользовать.
     Подходит частично? -> дополнить локально, не меняя чужой контракт без причины.
     Не подходит? -> реализовать минимально новое.
  6. Каждая нетривиальная защита/обёртка имеет реальное основание?
     Нет -> не добавлять или удалить при review.
  7. Проверить diff по требованиям, 1С-инвариантам и тестам.
  8. Остановиться, когда решение достаточно проверено.
```

**Непроверенное критичное предположение** приводит к блокировке зависимой операции, а не к выдуманному fallback. **Низкий риск** допускает завершение исследования после достаточного ограниченного поиска без притворства, что существующих альтернатив гарантированно нет.

## Приложение C. Проверенные публичные ориентиры и ограничения источников

- [OpenViking: MCP Integration Guide](https://github.com/volcengine/OpenViking/blob/main/docs/en/guides/06-mcp-integration.md), [Capability Reference](https://github.com/volcengine/OpenViking/blob/main/docs/en/agent-integrations/16-capability-reference.md): нативный `/mcp` и наличие операций поиска, записи, удаления и управления доступом. Это **причина требовать реальный read-only**, а не утверждение, что отдельная установка уже защищена.
- [OpenViking: Codex Memory Plugin](https://github.com/volcengine/OpenViking/blob/main/docs/en/agent-integrations/04-codex.md): hooks recall/capture/commit сессий. KORA не подключает этот механизм в общий поиск команды.
- [andromanpro/1c-ai-connector: SECURITY.md](https://github.com/andromanpro/1c-ai-connector/blob/main/SECURITY.md): исходный `execute_query` и модель доступа под правами пользователя, а также существование технических read+update прав для обслуживания лимитера/аудита. Это не доказательство безопасности создаваемой KORA-адаптации.
- [Codex: AGENTS.md](https://developers.openai.com/codex/guides/agents-md/): инструкция проекта влияет на поведение агента; выполнить задачу и проверить результат всё равно требуется фактически.

Внешние документы — изменяющиеся страницы upstream. **Перед реализацией** привязать проверенные утверждения к конкретным версиям/коммитам библиотек; ни одна ссылка здесь не свидетельствует о результатах испытаний живого окружения.

**Итоговый принцип:** Codex должен перестать заново искать уже известное, писать уже существующее и защищаться от вымышленных отказов. За счёт этого разработчик 1С получает меньше, понятнее и надёжнее проверяемых изменений, без потери реальных гарантий продукта.
