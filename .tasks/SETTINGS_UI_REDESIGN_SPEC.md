# 1C AI Core — дизайн и требования к новой форме настроек

Статус: согласованная концепция для реализации в Codex. Источник: `ShadobaAI/edt-ai-core`, ветка `develop`, исходный UI `ui/settings.html`. Приложение `settings-mockup.html` — автономный интерактивный макет, **не реализация MCP/backend**.

## 1. Цель и границы

Уменьшить когнитивную нагрузку на пользователя и обеспечить полное редактирование обоих профилей без ручного открытия файлов. Повторно использовать существующие backend-операции, схемы и проверки; не создавать параллельную бизнес-логику в браузере.

В результате должны быть:

1. Три раздела: **Компоненты**, **Конфигурация**, **Поддержка**.
2. Компактная шапка с выбором проекта, агрегированным состоянием и краткой причиной неготовности.
3. Два проектных профиля: общий `.ai/project.yaml` и локальный `.ai/project.local.yaml`.
4. Два режима одного редактора: **Поля** (100% схемы) и **YAML** (сырой текст).
5. Контекстные подсказки рядом с параметрами; отдельной вкладки «Справка» нет.

Не входит в задачу: изменение стандартов 1С, логики EDT/code-index/BSL LS, установка внешних сервисов, перенос документации GitHub в интерфейс. Макет показывает типовые состояния и фиктивные данные; не обещает работающие backend-операции.

## 2. Каркас интерфейса

### Шапка

Слева — знак/название `1C AI Core`. Затем селектор текущего проекта: название, поиск по истории, путь, команда «Открыть другой каталог». Список проектов **не занимает постоянную боковую панель**. Переключение проекта при несохранённом черновике блокируется до сохранения/отмены; реальный каталог текущего чата нельзя подменять историей другого чата.

Справа — агрегированный статус (иконка, короткий заголовок и максимум две краткие причины), обновление. По нажатию на проблемный статус открывается раздел «Компоненты» с фильтром проблем. На узком экране шапка переносится на две строки без горизонтального скролла.

Под шапкой — три вкладки. Внутри разделов нет повторной навигации по проектам.

### Визуальный стиль

- Плотность: инженерная, компактная; основные элементы 36–40 px по высоте, вторичные кнопки 30–32 px.
- Оформление: спокойные поверхности, нейтральные границы, один акцент для действий; не оформлять каждую настройку отдельной тяжёлой карточкой.
- Цвет не единственный сигнал статуса: текст/иконка обязательны.
- Светлая/тёмная тема через переменные Codex/MCP App с безопасными fallback.
- Без внешних шрифтов, CDN и сетевых UI-зависимостей.
- Адаптивность: сетка карточек 2 колонки на широком экране и 1 на узком; поля и кнопки не обрезаются.

## 3. Раздел «Компоненты»

### Каталог

Группы: внешние MCP (EDT, v8std, OpenViking); управляемые сервисы (Code Index, BSL LS); профильные возможности (YaXUnit, Vanessa). В дальнейшем новые компоненты добавляются в существующий каталог, а не новой вкладкой.

Каждая карточка: название, назначение одной строкой, статус, короткая причина при проблеме, установленная/эффективная версия (если применимо), одна основная команда «Настроить»/«Управление». Подробные настройки открываются в диалоге или компактной подробной панели; технические параметры не отображаются в общей сетке.

При работе с компонентом показывать **источник эффективного значения**: общий профиль, локальный профиль, глобальная пользовательская настройка, внешний файл или переменная окружения. Нельзя скрывать приоритетный внешний override: пользователь не должен считать запись в YAML действующей, если она перекрыта.

### Состояния и агрегирование

Раздельные состояния компонента:

| Состояние | Значение | Влияние на сводный статус |
| --- | --- | --- |
| Готов | Обязательная проверка пройдена и актуальна | ОК |
| Требует подготовки | Не выполнена установка, индексирование или назначение | Предупреждение, если обязателен |
| Недоступен / ошибка | Нужный сервис не отвечает либо отказал | Ошибка, если препятствует работе |
| Отключён | Явно выключен настройкой | Нейтрально, если необязателен |
| Не настроен | Отсутствует обязательная конфигурация | Предупреждение или ошибка по зависимости |
| Не проверен / устарел | Нет свежего результата для текущего проекта/ревизии | Нельзя отображать «Готов» |
| Проверяется / операция | Идёт запрос или длительная операция | Отдельное промежуточное состояние |

Агрегированный статус считается только для выбранного проекта и необходимых ему возможностей. Приоритет: критическая ошибка → требует внимания → проверка/неизвестно → готово. Необязательная отключённая интеграция не является ошибкой. Статус включает время/ревизию проверки; изменение профиля или проекта делает прежний результат устаревшим.

Обновление состояния пассивное и не должно само скачивать, устанавливать, запускать, перезапускать сервисы или перестраивать индекс. Такие операции выполняются только после явного выбора и требуют защиты от повторного запуска/двойного нажатия.

## 4. Раздел «Конфигурация»

### Два файла и наследование

| Режим | Файл | Смысл |
| --- | --- | --- |
| Общий · Git | `.ai/project.yaml` | Переносимые настройки проекта |
| Локальный | `.ai/project.local.yaml` | Личные/машинные переопределения, Git-ignored |

Слои `.ai/instances/*.local.yaml` и пользовательские instance overrides **удаляются из модели настроек**. `EDT_AI_INSTANCE` допускается оставить как технический идентификатор runtime/сессии, но он не задаёт третий слой конфигурации. Глобальные настройки плагина (например, версии управляемых runtime-компонентов) остаются отдельными настройками продукта, а не третьим проектным профилем.

Уровни приоритета документировать точно по каждому параметру: глобальный default → общий проектный профиль → локальный профиль → разрешённые внешние файл/переменная окружения. Не предполагать одинаковый приоритет для всех ключей без проверки текущего resolver.

### Режим «Поля»

**Источник структуры — действующие схемы** `schemas/project-profile.schema.json` и `schemas/project-local.schema.json`. Не поддерживать вручную второй неполный список полей. В форме должны быть доступны все свойства схемы, включая отсутствующие сейчас необязательные, вложенные объекты, массивы, словари с динамическими ключами, `enum`, `const`, boolean, числовые, строковые и nullable значения.

Обязательные секции: основное (`schema_version`, `profile_id`, `profile_version`, `project`), репозитории и корни (`repositories`, `roots`), назначенные инструменты (`authorities`), политика (`policy`), тестирование (`testing`), знания (`knowledge`), совместимость (`compatibility`), подключения (`connections`) и компоненты (`components`). Если в схеме появляется новый раздел, он автоматически доступен как дополнительный, без изменения HTML-разметки.

Поведение:

- Отсутствующее необязательное поле показывает «+ Добавить», заданное поле — значение и «Удалить/наследовать»; отличать отсутствие от `null`, `false`, `0` и пустой строки.
- Массивы поддерживают добавление, удаление и порядок элементов; объекты-элементы содержат полный набор дочерних полей.
- Для словарей предусмотрено добавление/удаление произвольного валидного ключа.
- Для `enum` — select; для `const` — отображение неизменяемого значения; для nullable — явный выбор `null`.
- Поля группируются в раскрываемые секции, первые две можно раскрывать по умолчанию. Никакой искусственной пагинации, скрывающей параметры.
- Подсказка `?` раскрывает короткое объяснение «что это / когда менять / последствия». Сначала использовать имеющиеся описания схемы; дополнительные тексты вести в одном компактном каталоге. Не копировать GitHub-документацию.
- Семантические связи (ID репозитория, `edt_project`, выбранные коллекции, ограничения путей) проверяет существующий backend, а не только клиентский тип поля.

### Режим «YAML»

Текст текущего файла, без JSON-представления и без режима «дерево JSON». Два режима используют **один черновик**, а не два независимо редактируемых документа.

Реализация должна использовать YAML AST или эквивалент, сохраняющий комментарии, ключи и форматирование вне изменённых узлов. При переключении «Поля → YAML» внесённые изменения сериализуются; при обратном переключении YAML разбирается, ошибки показываются с номером строки, а черновик не теряется. Недопустимо без предупреждения перезаписывать комментарии через `JSON.stringify` или полную пересериализацию.

Валидация: синтаксис YAML, schema, project-local merge, профильные cross-field ограничения, containment путей, совместимость и безопасность. Отмечать ошибки возле соответствующих полей и в общей панели результатов. Сохранение только после preview изменений и проверки исходной revision. При конфликте внешнего изменения — перечитать/сравнить, не перезаписывать молча. Должны сохраняться резервные копии и работать rollback при ошибке записи.

### Черновики

- При смене профиля, режима, проекта, раздела и закрытии не терять изменения. Смена вкладки внутри одного документа не требует сохранения.
- «Отменить изменения» откатывает текущий документ к загруженной версии; «Проверить» не изменяет файлы; «Сохранить» применяет только подтверждённый diff.
- Переключатель области общего/локального профиля при черновике предлагает сохранить, отменить или остаться; не переносит значения из одного слоя в другой автоматически.
- Режим просмотра исторического проекта без привязки к чату остаётся read-only.

## 5. Импорт и экспорт

Из раздела «Конфигурация» — отдельные диалоги с выбором области:

| Область | Экспорт | Импорт |
| --- | --- | --- |
| Общий | `.yaml` | YAML + предпросмотр изменений общего файла |
| Локальный | `.yaml` | YAML + предпросмотр изменений локального файла |
| Оба | `.zip` с двумя известными путями | ZIP с раздельным предпросмотром обоих файлов |

ZIP не должен включать состояние runtime, логи, историю, credentials, OpenViking-ключи и сторонние файлы. Импорт ограничивает размер и количество entries, запрещает traversal, абсолютные пути, symlink и дубли имён; manifest с версией формата допустим. Перед применением показать целевые файлы, различия, удаляемые/изменяемые поля, машинно-зависимые значения и действие с уже существующими файлами. Отдельное подтверждение замены, backup и atomic-write. Секреты не экспортировать автоматически; локальные URL/пути могут быть чувствительными — явное предупреждение.

При импорте старого JSON допускается временная совместимость backend, но редактор и основной сценарий пользователя остаются YAML. Не смешивать импорт профиля с импортом глобального `settings.json`.

## 6. Раздел «Поддержка»

Содержит:

1. Информация: версия плагина, Node.js/OS, контекст и путь проекта, версии управляемых компонентов, последняя операция.
2. Журнал: поиск, фильтр уровня, время/компонент/событие, раскрытие деталей, отображение текста без HTML-интерпретации.
3. Диагностический пакет: экспорт ограниченного, санитизированного отчёта с версиями, состоянием и логами; отдельно экспорт подробного журнала с выбором периода и предупреждением о путях/адресах.
4. Внешняя ссылка на исходный репозиторий и полную документацию, без встроенного дублирования.

Никаких отправок отчёта на сервер без отдельного действия пользователя. В отчёте маскировать известные секреты; явно сообщать, что пути и адреса серверов могут остаться. Не собирать историю чатов или исходный код.

## 7. Диалоги, доступность и host API

Короткие операции — диалог: настройка компонента, выбор версии, импорт/экспорт, подтверждение записи. Полноразмерный YAML-редактор не помещать в модальное окно. Базовый вариант — нативный HTML `<dialog>` внутри MCP App; использовать host modal API только после feature detection и проверки в целевом Codex. На закрытие по Escape/кнопке/подложке обеспечить возврат фокуса; при черновике спрашивать подтверждение.

Доступность: семантические вкладки, `aria-selected`, `role=tabpanel`, подписи полей и сообщений ошибок, управление Tab/стрелками где уместно, видимый фокус, скринридерные статусы через `aria-live` без спама, достаточный контраст, `prefers-reduced-motion`, отсутствие hover-only функциональности.

## 8. План реализации

1. **Контракты**: аудит реальных настроек и источников; перечень всех полей схем и активных override, подготовка migration plan для экземпляров.
2. **Backend**: две области профиля, миграция с резервными копиями и разбором конфликтов; единый источник YAML/AST, schema-derived metadata, безопасные preview/apply и revision.
3. **UI shell**: новый header/project selector/status/tabs; сохранить историю проектов и ограничения контекста чата.
4. **Компоненты**: карточки и диалоги поверх существующих `settings.*` операций; корректные статусы и ограничения прав.
5. **Редактор**: генерация всех полей по схемам, синхронизация с YAML, подсказки, валидация, diff, undo/save.
6. **Перенос и поддержка**: YAML/ZIP import/export и журнал/отчёты.
7. **Тесты и ручная проверка**: существующий MCP и browser UI, Windows file picker, узкие экраны, dark mode, доступность, реальные host dialogs.

Не переписывать backend ради UI без необходимости: где существующие `settings.preview/apply/edit`, `settings.operation`, readiness и diagnostics удовлетворяют контракту, использовать их. При новой структуре допустимо вынести из большого `ui/settings.html` стили и независимые UI-модули, но готовый MCP resource по-прежнему должен работать в sandbox Codex и собираться текущим package workflow.

## 9. Критерии приёмки

- [ ] На первом экране нет постоянной боковой панели профилей, лишних селекторов области и технических форм.
- [ ] Выбор проекта в шапке сохраняет функциональность истории/поиска/открытия каталога, не нарушая isolation чата.
- [ ] Три раздела: Компоненты, Конфигурация, Поддержка; отдельной Справки и JSON-редактора нет.
- [ ] Status не сообщает «готово» для отключённого обязательного, непроверенного, устаревшего или ошибочного компонента.
- [ ] Все свойства `project-profile.schema.json` и `project-local.schema.json`, включая optional/nested/list/map, достижимы из визуальной формы без ручного редактирования файла.
- [ ] Поля и YAML — один черновик; комментарии и неизвестные при текущей версии допустимые значения не теряются при round-trip.
- [ ] `null`, отсутствие ключа, пустая строка, `false` и `0` не смешиваются.
- [ ] Для проекта ровно два слоя; старые instance override корректно мигрированы или явно предъявлены как конфликт.
- [ ] Новые и старые проверки схемы/путей/безопасности и optimistic revision действуют при любом способе редактирования.
- [ ] Импорт/экспорт: общий, локальный, оба ZIP; есть preview и backup, секреты исключены.
- [ ] Диагностика доступна без готового профиля; выгрузка не отправляет данные в сеть.
- [ ] Диалоги клавиатурно доступны, не теряют фокус/черновик; интерфейс работает на узком экране и в обеих темах.
- [ ] Автотесты покрывают изменение каждого типа JSON Schema-поля, schema evolution, конфликт ревизий, повреждённый YAML, архивные атаки и migration конфликтных instance values.
- [ ] Локальные проверки пройдены; реальное поведение окна Codex и системного picker подтверждено ручным тестом.

## 10. Что демонстрирует HTML

`settings-mockup.html` содержит данные из эталонного профиля и полные схемы из текущего `develop`. Он демонстрирует структуру, адаптивность, переключение разделов/областей, полный обход свойств схемы, карточки компонентов, диалоги, фильтрацию логов, контекстные подсказки и базовое отображение YAML. Его интерактивность **не доказывает** безопасность миграции, парсинг произвольного YAML, реальную диагностику, установку сервисов, импорт ZIP, применение файлов или поддержку host-controlled modal.
