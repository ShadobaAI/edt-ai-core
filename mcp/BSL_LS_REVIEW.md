# Review BSL LS: несколько конфигураций

## Проверенный контракт

Сверены предоставленные локальные `docs/en/features/McpMode.md`,
`McpWorkspaceBootstrap`, `McpWorkspaceResolver`, `McpDocumentReader`,
`McpRootsBootstrapper`, `McpRootsChangeConsumer`, инструменты workspace и оба
загрузчика `LanguageServerConfiguration`/`GlobalLanguageServerConfiguration`.
Для EDT-MCP проверены `ListProjectsTool`, описания `list_projects` и
`list_configurations`.

| Возможность | Предоставленные исходники BSL LS | Проверенный установленный JAR |
| --- | --- | --- |
| Несколько workspace | Отдельные контексты и настройки; файл выбирает свой контекст, справочные операции требуют `workspaceFolder` | Несколько roots подтверждены двумя успешными контекстными запросами |
| `roots/list` | Bootstrap при объявленной capability, синхронизация изменений roots | Подтверждены начальные два root и добавление третьего после уведомления |
| Переключение roots | Синхронизация асинхронна относительно запросов клиента | Первый запрос к новому root пришёл до регистрации; следующий после синхронизации успешен |
| `register_workspace_folder` / `list_workspace_folders` / `unregister_workspace_folder` | Есть; регистрация возвращает результат после индексации, повторная регистрация не переиндексирует | Отсутствуют в живом каталоге |
| Контекст справочных операций | `workspaceFolder` | Старый параметр `root`; `workspaceFolder` отсутствует |

Таким образом, предоставленные исходники и установленный артефакт имеют разный
MCP API. Проверка нового binding отклоняет этот JAR с перечислением недостающих
возможностей. Совместимость с API только через roots не реализуется; компоненты
не обновлялись, номера версий не закреплялись. Положительная live-приёмка нового
маршрута требует JAR с нативными workspace-инструментами. Сборка предоставленных
исходников здесь не выполнялась: локального подготовленного Gradle runtime нет.

## Исправленные дефекты

| Приоритет | Проблема | Результат |
| --- | --- | --- |
| P1 | Единственный `--root`, автоматическая индексация всего каталога, обязательный выбор одного репозитория | Выбранный project root задаёт границу доступа; конкретные конфигурации регистрируются штатными инструментами BSL LS |
| P1 | Обязательный конфиг и генерируемый пустой JSON меняли штатную загрузку настроек | Конфиг необязателен; без явного пути загрузку выполняет BSL LS |
| P1 | CLI `--configuration` менял глобальные параметры, но не задавал путь фабрике workspace-настроек | Явный файл передаётся в `McpCommand` и через `app.configuration.path` в фабрику |
| P1 | EOF только закрывал stdin; зависшая JVM могла пережить клиента | Ограниченное graceful-завершение с принудительным завершением собственного дочернего процесса |
| P1 | Регистрация/удаление индекса могли пересекаться с анализом | Инструменты выполняются последовательно; протокольные ответы и уведомления обслуживаются отдельно |
| P2 | ID встречного запроса сервера мог совпасть с ID запроса клиента | Раздельное отображение ID в обоих направлениях, контроль дубликатов и ответа только своему запросу |
| P2 | Unicode-файл заменялся 8.3-путём, а URI мог попадать в Java как имя файла | UTF-8 stdio, канонический путь и преобразование file URI в filesystem path без 8.3 |
| P2 | Проверки относились только к `file`; новые workspace-параметры расширяли доступ | Проверяются `path` регистрации, `workspaceFolder` и `file`, включая realpath/junction; очередь повторно проверяет пути перед отправкой |

Состояние регистраций и выбор контекста остаются в BSL LS. Discovery EDT остаётся
в EDT-MCP: Codex берёт точное имя и путь из `list_projects`, затем передаёт путь
в BSL LS. `list_configurations` перечисляет конфигурации запуска, а не каталоги
исходников. Каталоги вне выбранного binding отклоняются. Другой каталог или
сессия Codex использует свой процесс и свои регистрации. Отдельный реестр
конфигураций или инструмент выбора активной конфигурации в прокси не добавлен.

## Необязательные настройки

`mcp.managed.bsl-ls.configuration` принимает относительный путь от project root
или явный абсолютный путь. Указанный отсутствующий файл отклоняется до установки
runtime и запуска JVM. Файл с именем `bsl-language-server.json` без точки
поддерживается явным параметром. Содержимое и семантику параметров читает BSL LS.

Без явного пути используется нативное имя `.bsl-language-server.json`.
Фактическая фабрика сначала проверяет файл в CWD процесса, затем в workspace,
затем в домашнем каталоге. Явный файл имеет приоритет для всех зарегистрированных
workspace. Это выбор одного файла загрузчиком BSL LS, не объединение настроек
прокси. Для отдельных настроек конфигураций следует использовать файлы в их
workspace и учитывать наличие общего файла в CWD. Изменение startup-пути настроек
переподключает binding; смена контекста между workspace перезапуска не требует.

## Воспроизводимые проверки

Транспортные тесты запускают реальный Node-прокси с подменой только дочернего
сервера. Они проверяют несколько конфигураций и сессий, Unicode/URI, конфиг,
границы и junction, замену каталога во время ожидания, пересекающиеся ID,
отмену очереди, внезапный выход и EOF зависшего процесса. Они не доказывают
корректность диагностик самого BSL LS.

Локально пройдены 132 Python-теста, 10 транспортных сценариев прокси и существующие
Node-проверки Vanessa. После нативных проб JVM с тестовым JAR не осталось.

```text
node --test tests/test-bsl-ls-proxy.mjs
node tools/test.mjs
```

Нативный приёмочный сценарий не скачивает и не устанавливает компонентов.
Он создаёт синтетические Unicode-проекты и проверяет регистрацию, переключение,
разные workspace-настройки диагностик, явный файл без точки, параллельные сессии
и сохранение второй сессии после закрытия первой:

```text
node tests/bsl_workspace_smoke.mjs --jar C:\runtime\bsl-language-server-exec.jar
```

На установленном артефакте сценарий подтверждённо останавливается на проверке
контракта до анализа исходников. Полноценная live-проверка регистрации и загрузки
workspace-настроек на совместимом артефакте остаётся непроведённой. Рабочие
конфигурации пользователя и их настройки не менялись.
