# Профили проектов

Профиль связывает универсальные навыки плагина с конкретным проектом:
репозиториями, индексными aliases, проектами EDT, защищёнными путями
и тестовыми возможностями. Это данные YAML, а не исполняемый адаптер.
`project.adapter` — описательная метка; она не загружает проектный код.

## Какие файлы за что отвечают

```text
project/
  AGENTS.md                  инструкции Codex
  .ai/
    PROJECT.md               назначение, архитектура и источники истины
    project.yaml             переносимый профиль
    project.local.yaml       личные overrides, вне Git
    instances/
      dev.local.yaml         overrides именованного экземпляра, вне Git
  src/                       пример каталога исходников
```

Профиль и инструкции храните в Git проекта. Личные overrides и резервные копии
с адресами/параметрами окружения не публикуйте. `profile init` создаёт `.ai/.gitignore`
для `project.local.yaml` и `instances/*.local.yaml`; правила для резервных копий
при необходимости добавьте сами.

Отдельно плагин хранит пользовательское состояние в `${CODEX_HOME}/1c-ai-core`
(по умолчанию `~/.codex/1c-ai-core`): общие настройки, загруженные runtime,
индексы, историю, диагностику и overrides экземпляров. Оно не переносится
в репозиторий и не входит в установочный ZIP.

## Создание через чат

Откройте папку проекта и попросите: **«Создай и настрой профиль 1C AI Core»**.
Агент создаст шаблон `generic-1c`, уточнит только недостающие сопоставления
и поможет проверить подключения. Существующий профиль не перезаписывается
командой создания; для изменения используется редактор или импорт с предпросмотром.

При создании добавляются только отсутствующие `AGENTS.md`, `.ai/PROJECT.md`
и `.ai/.gitignore`. Их минимальный текст требует заполнения под ваш проект:
[как подготовить проектный AGENTS.md](PROJECT_AGENTS.md#как-создать).
Создание возвращает списки добавленных/сохранённых инструкций и
`contentValidated: false`; это не проверка полноты правил команды.
Существующий `AGENTS.override.md` сохраняется и включается в `preserved`;
если он непустой, поле `overrideFile` сообщает о его приоритете над `AGENTS.md`.
Каталоги вместо вспомогательных файлов отклоняются до записи профиля.

## Минимальный заполненный профиль

Ниже пример для одного репозитория с исходниками в `src/`. Имя `Application`
нужно заменить точным именем проекта в EDT; остальные значения тоже относятся
к примеру, а не к встроенному проекту плагина.

```yaml
schema_version: '0.2'
profile_id: generic-1c
profile_version: 0.2.0
project:
  id: application
  adapter: generic-1c
  purpose: Разработка прикладной конфигурации
repositories:
  - id: application
    path: .
    alias: application
    edt_project: Application
roots:
  source: [src]
  protected: [src]
authorities:
  edt_writer: edt
  code_index: code-index
  bsl_ls: bsl-ls
  v8std: v8std
policy:
  mode: conservative
  edt_repository_ids: [application]
testing:
  commands: []
  yaxunit: false
  vanessa: false
knowledge:
  mode: disabled
  provider: none
  manifest: null
  collections: []
  required: false
  dependent_actions: []
compatibility:
  core: '>=0.1.0'
```

Контракт проверяет [project-profile.schema.json](../schemas/project-profile.schema.json),
дополнительные ограничения — [profile.mjs](../scripts/profile.mjs).

| Поле | Назначение |
| --- | --- |
| `schema_version` | Версия структуры данных; сейчас строка `'0.2'` |
| `profile_id`, `profile_version` | Идентификатор и версия переносимого профиля; `project.id` отдельно идентифицирует проект |
| `repositories[].id` | Уникальная ссылка на репозиторий в policy и testing |
| `repositories[].path` | Путь от каталога профиля до корня репозитория |
| `repositories[].alias` | Уникальное имя для code-index |
| `repositories[].edt_project` | Точное имя проекта EDT; `null` допустим в схеме для репозитория без назначения |
| `roots.source`, `roots.protected` | Каталоги, закрытые для общего filesystem/shell-доступа; guard использует объединение списков |
| `authorities` | Назначенные роли: EDT writer, code-index, BSL LS и v8std |
| `policy` | Привязка EDT-репозиториев и дополнительные ограничения/нормативные исключения |
| `testing` | Команды и настройки YaXUnit/Vanessa; включённый вид тестов требует соответствующего config |
| `knowledge` | Режим, провайдер, manifest, collections/collection_uris, обязательность, зависимые фазы и бюджеты поиска |
| `compatibility.core` | Требование к версии запущенного ядра, проверяемое при загрузке |

Пути должны быть относительными, без `..` и выхода за корень проекта,
включая выход через symlink/junction. IDs и aliases репозиториев уникальны.
`edt_repository_ids` и `unbound_edt_repositories` ссылаются только на известные
репозитории и не пересекаются. Неизвестные поля отклоняются схемой.
Проектные исключения норм не отменяют общую action policy или защиту исходников.

### Версии контрактов

| Документ | Поле и принимаемая версия |
| --- | --- |
| Профиль проекта | `schema_version: '0.2'` |
| Полные настройки плагина | `version: '0.1.0'` |
| Экспорт/редактор настроек `1c-ai-core-settings` | числовое `version: 1` |
| Manifest знаний | `schema_version: '0.1'` |
| Метаданные материала | `schema_version: '0.1'` |
| Подтверждение публикации | `schema_version: '0.2'` |
| Локальные/instance overrides | необязательное `schema_version: '0.1'`; прежний формат без маркера поддерживается без изменения семантики |

Версии не выводятся из `profile_version`, версии плагина или редакции знаний.
Версия выпуска из `plugin.json` описывает код плагина. Git-редакция знаний
находится только во внешнем publication receipt, `index_revision` обозначает
снимок индекса, а `revision` материала — его собственную редакцию. Обновление
плагина не публикует знания и не меняет эти значения. Manifest хранит состав
и хеши материалов; поля Git-коммита, включающего этот manifest, в нём запрещены.
Издатель сначала фиксирует manifest в Git, затем связывает полный commit ID,
хеш точных байтов manifest и индекс во внешнем receipt. Receipt хранится вне
этого коммита: циклическая самоссылка не вычисляется и не подставляется.
Несовместимая, отсутствующая обязательная либо неверно типизированная версия
отклоняется до интерпретации полей и записи с ошибкой `UNSUPPORTED_CONTRACT_VERSION`
(для оболочки экспорта — ошибка неизвестного формата/версии). Частичный локальный
overlay настроек плагина может не содержать `version`: это прежний контракт
`0.1.0`, наложенный на defaults; заданная версия обязательно проверяется.

Профиль `0.1` автоматически не мигрирует в `0.2`: проверьте ID коллекций,
`provider: none` с `manifest: null` и без `search`, формат manifest/метаданных
и относительные пути, затем явно измените `schema_version` и повторите валидацию.
Сначала сохраните исходный профиль. При откате плагина восстановите совместимую
версию профиля отдельно от индекса знаний; новая схема не должна молча
интерпретироваться старым плагином. Локальные overrides и версия настроек
в этом изменении сохраняют прежнее значение и приоритеты.

Согласованный набор текущего кода: plugin/package `0.4.2`, каталог skills
`0.1.0`, policy protocol `2.1.0` с registry schema `2`, registry
`2026-10-20.1`, action policy/default settings `0.1.0`. Каталог skills — версия
формата, а не идентификатор точных байтов. Для чистой сборки содержание задаёт
commit; `build-info.json.dirty` лишь отмечает наличие незакоммичённых изменений.
Для dirty-сборки сохраните сам снимок и хеши файлов/ZIP: commit и флаг её
содержимое не идентифицируют. Версии прикладных контрактов перечислены выше. Readiness cache принимает
только числовую версию `3`; отсутствующая, старая или будущая версия даёт
`not_checked` без загрузки прежнего диагностического текста и без перезаписи.
Нужна новая setup-проверка. Журнал diagnostics формата `2`; старые записи
показывают только безопасные метаданные, без прежних messages/stacks.

Откат кода и откат знаний — отдельные решения. Перед переключением сохраните
профиль, overrides и состояние вне plugin cache; остановите или переподключите
свои MCP-сессии. Используйте проверенную копию плагина с совместимыми схемами
и явным отказом неизвестных версий. Если целевой старый код не гарантирует
такой отказ, его запуск с новым состоянием не поддерживается: сначала нужна
отдельная совместимая копия состояния. Не понижайте маркер версии вручную для
обхода валидации. Возвращайте пакет через штатный механизм хоста, не заменяя
код работающего процесса. После переключения заново проверьте binding/setup;
готовность, полученная с другим набором skills/policy, не переносится.
Публикацию/индекс знаний и пользовательские исходники этот процесс не меняет.

## Несколько репозиториев

Разместите профиль в общем корне рабочего пространства, а все репозитории —
внутри него. Например: `product/`, `unit-tests/`, `framework/`, `ui-tests/`.
Для каждого задайте отдельные `id`, `path`, `alias` и соответствующее EDT-имя.
Не используйте `../sibling`: такой путь не пройдёт проверку.

Плагин ищет профиль в выбранном каталоге и выше до границы Git. Если его нет,
проверяет вложенные каталоги. Один найденный профиль может быть выбран,
несколько дают неоднозначность: откройте конкретную папку. Discovery пропускает
служебные каталоги, symlinks и дерево `src` у найденного EDT-проекта;
не стоит размещать профиль внутри исходников конфигурации.

Несколько репозиториев в одном профиле обслуживает его назначенный EDT endpoint.
Для независимо выбранных контуров используйте отдельные профили/экземпляры
и серверы EDT. Пример структуры —
[multirepo-workspace](https://github.com/ShadobaAI/edt-ai-core/tree/main/examples/multirepo-workspace).

## Подключения и экземпляры

`connections.edt`, `connections.v8std` и `connections.openviking` в переносимом профиле необязательны.
Публичные безопасные defaults можно хранить там; машинные адреса удобнее
задавать через форму или `.ai/project.local.yaml`.

Пример **локального** файла; адреса условные, их нужно заменить:

```yaml
connections:
  edt:
    url: http://127.0.0.1:18080/mcp
  v8std:
    url: http://127.0.0.1:18081/mcp
    headers_env:
      Authorization: V8STD_AUTHORIZATION
components:
  bsl-ls:
    enabled: false
```

В `V8STD_AUTHORIZATION` передаётся полное значение заголовка, например
`Bearer …`. Значения секретов не записывайте в YAML или URL.
Локальный формат проверяет [project-local.schema.json](../schemas/project-local.schema.json).
Он поддерживает `connections` и overrides `components` для code-index/BSL LS;
это не второй переносимый профиль.

Транспорт OpenViking в `mcp.optional.openviking` пользовательских настроек
принимает булевый `enabled`, HTTP(S) `url` без credentials, query и fragment,
`headers_env` (имя заголовка → имя environment-переменной с полным значением),
`timeout_seconds` (> 0, до 300, по умолчанию 20) и `max_response_bytes`
(1024–16777216, по умолчанию 2097152). Секреты разрешаются только в момент
запроса; отсутствующая переменная авторизации приводит к отказу подключения.
Диагностическая проба ограничивает таймаут сверху 30 секундами. Сохранённые
настройки ещё не подтверждают готовность поиска через клиентский адаптер.
OpenViking необязателен и по умолчанию выключен. Для подключения нужны
`enabled: true` и непустой effective URL. `enabled: false` сохраняет адрес
и параметры, но запрещает соединение. Отключённый необязательный компонент
не блокирует общую готовность; обязательные знания и режим KORA сохраняют
свою блокировку зависимых действий. Изменение одного URL, включая переменную
окружения, не включает отключённый транспорт.

Порядок наложения от меньшего приоритета к большему:

1. Общие defaults и пользовательские настройки плагина.
2. `connections` из `.ai/project.yaml`.
3. `.ai/project.local.yaml`.
4. `.ai/instances/<instance>.local.yaml`.
5. Пользовательский файл `projects/<project-key>/instances/<instance>.yaml`
   в каталоге состояния плагина.
6. Файл из `EDT_AI_CONNECTIONS_FILE`.
7. Переменная `url_env` подключения либо стандартная `EDT_AI_EDT_URL`
   / `EDT_AI_V8STD_URL` / `EDT_AI_OPENVIKING_URL`.

`connections.openviking` принимает те же поля транспорта, что
`mcp.optional.openviking`, и необязательный `url_env`. Все поля необязательны:
например, профиль задаёт URL и авторизацию, локальный файл меняет лимиты,
а instance override — только URL. Форма/MCP `settings.update`
сохраняет `openvikingEnabled`, `openvikingUrl`, `openvikingTimeout`,
`openvikingMaxResponseBytes` и `openvikingHeadersEnv` только в текущий instance
override. Карта `headers_env` заменяется целиком на каждом явно заданном уровне;
пустая `{}` очищает унаследованные заголовки. В форме вводятся только имена
переменных окружения, значения credentials в неё не загружаются.
`connectionSources.openviking` показывает источник effective URL; остальные
поля наследуются независимо в том же порядке, их источники возвращаются в
`valueSources` и показываются рядом с полями формы. `openvikingEnabled`
наследуется независимо от URL; в форме это флажок «Использовать OpenViking».
В форме таймаут,
лимит ответа и заголовки собраны в блок «Дополнительные настройки OpenViking».
Сводка знаний показывает
выбранные коллекции, режим и область блокировки; редакция из свежей setup-пробы
не подтверждает готовность workflow другого подключения. Устаревшее подтверждение
не показывается как актуальная редакция. Секреты из environment в
effective-настройки не подставляются.

Preview показывает effective-транспорт OpenViking с лимитами; apply повторно
разрешает и проверяет конфигурацию под блокировкой. Изменение профиля, локального
файла, любого instance override или явного файла подключений делает прежний
preview/документ редактора устаревшим, даже если изменение скрыто другим override.
Требуется загрузить/проверить документ заново; автоматической перезаписи нет.
Экспорт переносит профиль и общие настройки, включая имена `headers_env`,
но не локальные/instance overrides и не значения environment. Авторизация в
URL и inline headers отклоняются; query в endpoint OpenViking не поддерживается,
чтобы credential не попал в переносимый URL.

Объекты объединяются по полям, массивы заменяются целиком. Явная пустая строка
локального URL отключает подключение и не заменяется автообнаружением.
Это относится и к OpenViking: пустая строка сохраняется при чтении, preview/apply
и импорте профиля; отсутствие поля означает наследование. Явная пустая URL-переменная
окружения также отключает транспорт и имеет высший приоритет. Для EDT, v8std
и OpenViking `enabled: false` сохраняет URL, но запрещает соединение.
Для намеренного возврата к наследованию
`settings.reset_connection` с `connection: openviking` удаляет только URL текущего
instance override, сохраняя флаг, лимиты и авторизацию. В форме этому соответствует
кнопка «Вернуть унаследованное значение» рядом с адресом из instance override.
Если EDT URL не задан, плагин может получить его из настроек workspace EDT.
Старый общий EDT URL применяется только при совпадении владельца `active_project`.

Имя экземпляра задаёт `EDT_AI_INSTANCE`, по умолчанию `default`.
Так один каталог может иметь разные локальные подключения. Переключение
экземпляра/подключения инвалидирует зависимый контекст этой MCP-сессии.
Один read-only v8std можно использовать нескольким проектам.

## Тесты и знания

Для YaXUnit укажите `testing.yaxunit_config`: репозиторий тестов,
`runner: edt`, каталог результатов и при необходимости framework/product mappings
и launch configuration. Включённому YaXUnit нужен назначенный EDT-проект
владельца тестов; framework и владелец тестов — разные репозитории.

Для Vanessa укажите `testing.vanessa_config`: владельца, `runtime_profile`,
`features`, `results`, `server_name`. Каталог feature-файлов должен находиться
внутри репозитория владельца. Внешнее окружение 1С/Vanessa предоставляется отдельно.

`testing.commands` содержит аргументы команды, владельца и объявленные эффекты.
Имя программы — переносимое имя исполняемого файла, без shell-выражения и пути.
Наличие команды в профиле само по себе не разрешает её запуск.

Раздел `knowledge` задаёт провайдер, относительный путь к manifest и выбранные
`collections`. ID коллекций — строчные латинские буквы, цифры, `.`, `_`, `-`
(до 64 символов, первый — буква или цифра). Manifest соответствует
[knowledge-manifest.schema.json](../schemas/knowledge-manifest.schema.json):
`kind: catalog` задаёт коллекции и разрешённые материалы (`id`, `collection`,
`path`, SHA-256 точных байтов файла); `kind: recommendations` содержит только
рекомендуемые коллекции и пустой `materials`, не является публикацией.
Объявленные ID и пути уникальны, каждый материал принадлежит объявленной
коллекции; выбор профиля не может ссылаться на неизвестную коллекцию manifest.
`manifest: null` допустим при подготовке подключения и не подтверждает публикацию.
При заданном пути загрузка/импорт профиля проверяет весь `catalog`, выбранные
коллекции, существование обычных файлов, SHA-256 их точных байтов, YAML front
matter, соответствие ID и активный статус. Пути материалов считаются от каталога
manifest; manifest остаётся внутри выбранного проекта, материалы и локальные
ссылки — внутри каталога manifest с учётом symlink/junction. Запрещены traversal,
абсолютные пути, Windows device names/ADS, неоднозначные сегменты и кодированные
разделители; повторные ссылки на один физический файл отклоняются.
Список рекомендаций нельзя назначать опубликованным каталогом.
При чтении опубликованного снимка через MCP OpenViking валидируются catalog,
выбранные коллекции и containment, а байты удалённого материала проверяются
адресно по manifest. Полного сканирования локальных исходных документов при
каждой retrieval-операции нет; это не заменяет полную проверку при импорте.

Необязательный `knowledge.search` задаёт полный объект требований:
`publication: verified`, `snapshot: consistent`, `access: read_only`,
`max_results` (1–100, по умолчанию 10), `max_excerpt_chars` (128–8000,
по умолчанию 1000), `max_material_chars` (1024–100000, по умолчанию 20000).
Это требования клиента к результату и бюджеты символов, не имена операций
внешнего MCP. Адаптер дополнительно ограничивает один запрос десятью кандидатами
и общим бюджетом выдачи; effectiveLimit и budgetLimited показывают это явно.

`provider: none` требует `manifest: null` и отсутствия `search`, явно отключает знания и сетевые обращения к
OpenViking. Для `provider: openviking` нужен непустой список выбранных коллекций;
весь рекомендуемый набор не требуется. Настроенный транспорт и успешная общая
MCP-проба ещё не подтверждают готовность поиска в этих коллекциях.
Для подключения явно задайте `knowledge.collection_uris`: отображение ID выбранных
коллекций в канонические `viking://resources/...` области существующего сервера.
ID коллекции и путь Git-manifest сами по себе не задают серверный URI; адаптер
не выводит его из локального пути. Отсутствие отображения не мешает загрузке
профиля, но не позволяет установить поисковое соединение. Личные области,
traversal и URI с кодированными разделителями не принимаются.
Контракт адаптера описан в [INTEGRATIONS.md](INTEGRATIONS.md).
Для OpenViking явно задайте `required` и `dependent_actions` (фазы `discovery`,
`design`, `implementation`, `review`, `runtime`). При `required: true` непустой
список определяет действия, заблокированные до подтверждения поиска.
`required: false` позволяет независимую работу без заявления покрытия знаний.
Эта проверка дополняет общую action policy и не даёт разрешений на действия.
`knowledge.mode` явно выбирает `disabled`, `transitional` или `kora`.
Для включённого провайдера режим обязателен; в режиме `kora` обязательно
`required: true`. Отсутствующий URL, выключенный транспорт или отказ сервера
сохраняют требования профиля. Автоматического перехода к `none` или ослабления
обязательности нет.
В `kora` перечисляются все пять фаз, и gate распространяется на весь штатный
workflow, в том числе на чтение, неизвестные новые операции, resources и prompts.
Relay проверяет его перед каждым native-вызовом и каждым элементом batch;
защита hook и CLI Vanessa сохраняют то же ограничение. Диагностика и настройка
для восстановления доступны. `knowledge.koraReady` остаётся `false`, пока нет
подтверждённого безопасного поиска: переходный режим и общий setup не являются
приёмкой KORA. Активация hook в реальном Codex проверяется отдельно.
Согласованные профили: `none` + `disabled` + пустые коллекции/зависимости +
`required: false`; либо `openviking` + `transitional`/`kora` с выбранными
коллекциями. При `required: false` зависимости пусты, при `true` — непусты.
Для совместимости прежний `provider: none` без новых полей остаётся явным
отключением; активный провайдер требует все поля явно. Схема отклоняет
противоречивый профиль. Включённый транспорт при `provider: none` даёт `invalid`
в диагностике и блокирует workflow без обращения к OpenViking. Выключенный
необязательный транспорт даёт `disabled`; выбранный провайдер, коллекции
и адрес сохраняются. При обязательных знаниях выключенный транспорт даёт
`not_configured`, сохраняя требования и блокировку. Включённый транспорт
с пустым URL также даёт `not_configured`. Сохранённый URL при выключенном
транспорте `none` допустим.
`knowledge.transport` в `settings.read`/`settings.status` отдельно сообщает
`enabled` и `endpointConfigured`: они описывают только effective-транспорт.
Режим, `required` и `dependentActions` берутся из профиля; изменение URL/флага
их не переписывает. При обязательном источнике пустой URL даёт `not_configured`
и сохраняет блокировку зависимых фаз; в KORA — всего штатного workflow.
Наблюдение и проверка не переписывают настройки для устранения противоречий.
Рекомендации в `knowledge/recommended-manifest.yaml` не расширяют выбранный
scope. `knowledge.coverageScope` в диагностике относится только к выбранным
коллекциям; `apiExistence: not_determined` означает, что состояние подключения
и покрытие сами по себе ничего не доказывают об отсутствии API.
Для MCP ИБ отдельные поля профиля пока не определены; произвольный `connections.database`
текущая схема не принимает.

## CLI для ручной работы

Команды выполняются из корня исходников или установленного плагина;
`PROJECT_DIR`, `PLUGIN_SETTINGS`, `PROFILE_FILE` — заменяемые пути.

```sh
node scripts/profile.mjs init "PROJECT_DIR"
node scripts/profile.mjs validate "PROJECT_DIR/.ai/project.yaml"
node scripts/profile.mjs effective "PROJECT_DIR" --settings "PLUGIN_SETTINGS"
node scripts/profile.mjs export "PROJECT_DIR" --output "PROFILE_FILE"
node scripts/profile.mjs import "PROJECT_DIR" --input "PROFILE_FILE" --replace
```

В CLI `validate` проверяет схему и семантику, но не готовность MCP и не фактические
пути относительно корня. Проверка containment выполняется при загрузке/import/effective.
`--merge` объединяет профиль того же `profile_id`; массивы заменяются.
Импорт поверх существующего профиля требует `--merge` либо `--replace` и создаёт backup.

Локальное назначение EDT для отдельного экземпляра:

```sh
node scripts/profile.mjs configure-instance "PROJECT_DIR" --instance dev --settings "PLUGIN_SETTINGS" --edt-url "EDT_MCP_URL"
```

Это записывает override в пользовательское состояние и не меняет переносимый
профиль. CLI без `--settings` использует `EDT_AI_SETTINGS`, затем
`settings/local.yaml` в корне плагина; MCP-серверы по умолчанию используют
`<state>/settings.json`. Для одинакового результата указывайте один файл явно.
