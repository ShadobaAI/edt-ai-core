# Policy и settings: пересмотр подхода

## Что изменено и почему

| Прежнее решение | Проблема | Принятый подход |
| --- | --- | --- |
| Общий URL до появления профиля | Настройка экземпляра B меняла A | Instance override существует независимо от профиля |
| Последний global active_project как выбор native settings | Пустой экран мог обращаться к чужому каталогу | Выбор принадлежит MCP-сессии; legacy CLI default сохраняется отдельно |
| Пустые roots как общая ошибка | Невозможно открыть начальный экран | Unselected отличается от ambiguous; чтение экрана остаётся доступным |
| Убийство bootstrap по общему таймеру | Дочерний backend мог продолжать действия после ошибки | Одна наблюдаемая операция с id, scope и итогом; timeout не считается отменой |
| Каждые пять секунд новая preparation | Повторные процессы и переподключения вместо ожидания | Polling статуса одной операции; новая проверка запускается явно |
| Успешный handshake как «готовность» | Обещание превышало evidence | Отдельно описаны protocol/API, index health, synthetic policy probe и неподтверждённая project readiness |
| «Atomic import» | Несколько файлов не образуют атомарную транзакцию | Атомарность каждого файла и rollback на перехваченной ошибке, без обещания crash recovery |
| OpenViking toggle без интеграции | Сохранённый флаг выглядел как работающий провайдер | Активация убрана из native layout; поля описаны как резерв конфигурации |

Import/export дополнительно проверен как перенос рабочего профиля, а не только
JSON roundtrip. Новый экспорт не несёт session root и legacy URL. Пустые URL
старого shared settings bundle не должны маскировать рабочие defaults профиля.
Схема optional settings теперь типизирована; неизвестные поля, например
`api_key`, и ошибочные типы отклоняются. Preview показывает изменения программ запуска и
effective URL, а environment/explicit override обозначаются своим источником.

## Почему policy пока не заменён

Текущая реализация согласованно проверяет selection, scopes, digest, additions,
фазы и ledger по заявленным assessments. Переименование `ledger_valid` в
«проект соответствует нормам», подпись caller evidence самим policy или
добавление локального эвристического BSL parser не усилили бы доказательство.

Нормализация assessments, подбор v8std, проверка EDT и разрешение записи имеют
разные источники истины. Protocol probe policy не проверяет ни один реальный
артефакт. Его документация теперь говорит о полноте относительно данного
selection и различает workflow-запрет записи от технического перехвата writer.
Исключённые HelpSearchServer/1c-docs-mcp и 1c-ssl-mcp не восстанавливались.

## Рекомендуемые следующие изменения

1. **Операции после перезапуска host.** Если требуется восстановление/отмена,
   добавить durable operation journal с папкой, instance, ревизиями файлов,
   стадией commit и результатом. Для нескольких файлов нужен recovery-протокол;
   один rename или blanket taskkill этого не решают. Отмену разрешать только
   в фазах с определённым исходом, с отдельным владением временными процессами
   и сохраняемым project daemon. Текущая память сессии не является таким журналом.
2. **Разделить prepare и inspect.** Оставить скачивание/запуск явной операцией,
   а refresh health/discovery делать через уже назначенный binding без перезапуска.
   Приёмка: повторный inspect не меняет PID, workspace registrations, toolsets
   и не пишет reconnect token. Сейчас каждое явное новое run_check — preparation.
3. **Убрать legacy глобальные endpoints в следующем несовместимом формате.**
   Для импорта назначать endpoint только явному scope; для общих read-only
   корпусов разрешить именованные connection references. Не заменять это общим
   active_project и не выдумывать уникальный instance по PID окна: такой ID
   нестабилен после перезапуска. Пока legacy CLI defaults сохранены без изменения.
4. **Технический gate — только при необходимости реального enforcement.**
   Нужны проверяемые receipts от EDT/index/v8std, corpus revision и связывание
   конкретной writer-операции с актуальным target/source revision. Добавлять gate
   следует в точке writer dispatch. Ещё одно self-reported поле или action checker
   с заявленным authorization evidence не аутентифицирует пользователя.
5. **Единый протокольный слой и сценарная приёмка.** Сократить дублирование
   JSON-RPC/schema обработки между settings/policy/relay, сохранив динамические
   контракты властей. Проверять malformed messages, lifecycle/cancellation,
   независимые JSON Schemas и end-to-end сценарии. Для policy нужны случаи
   пропущенных/лишних нормативных кандидатов и точного evidence, а не только
   успешное выполнение собственного validator.

Полная переделка policy ради единообразия с settings сейчас не обоснована:
settings владеет побочными эффектами, policy проверяет декларации. Их стоит
связать через явные контракты/evidence, сохраняя разные границы ответственности.
