# Разработка и сборка

Корень репозитория — исходники одного плагина `1c-ai-core`.
Техническое устройство описано в [ARCHITECTURE.md](ARCHITECTURE.md),
правила агента — в корневом `AGENTS.md`.

## Начало работы

Нужны Node.js 22+, npm и Git. EDT не требуется для изменения Node.js-кода
и локальных регрессий. Необходимое внешнее окружение подключается отдельно
для live-проверок интеграций.

```sh
git clone https://github.com/ShadobaAI/edt-ai-core.git
cd edt-ai-core
npm ci --ignore-scripts
node tools/vendor.mjs
```

Для всех дополнительных инструментов разработки нужен Node.js 22.19+ на
ветке 22, 24.11+ на ветке 24 или 26+. Эти требования относятся к инструментам
разработки; поддержка Node.js 22 для установленного плагина остаётся прежней.

`vendor.mjs` собирает runtime-библиотеки из lockfile в `vendor/deps.mjs`,
копирует готовые модули Koffi для поддерживаемых платформ и формирует `vendor/NOTICE.txt`.
Каталог `vendor/` генерируется и не хранится в Git. Изменяя зависимости,
обновляйте `package.json`, lockfile и проверяйте сведения о лицензиях.
В CI устанавливаются только `dependencies`: в них входит `esbuild`, необходимый
для сборки `vendor/`. Инструменты дополнительных локальных проверок остаются в
`devDependencies` и в CI не устанавливаются.

| Что менять | Где искать |
| --- | --- |
| Подключения Codex | `plugin.json`, `mcp.json`, `hooks/hooks.json` |
| Профиль и его загрузку | `schemas/`, `scripts/profile.mjs`, `project_context.mjs`, `selection.mjs` |
| Форму и настройки | `ui/settings.html`, `mcp/settings.mjs`, `scripts/settings_backend.mjs` |
| Запуск и обновление MCP | `scripts/runtime.mjs`, `lazy_mcp.mjs`, `mcp/bsl-ls-proxy.mjs` |
| Правила работы агента | `skills/`; принятые границы — `skills/catalog.yaml` |
| Нормативный протокол и guard | `policy/`, `scripts/guard.mjs`, `hooks/` |
| Поставку | `scripts/package_layout.mjs`, `tools/package-plugin.mjs`, `tools/check-plugin.mjs` |

## Проверки

Запускайте регрессии изменённого модуля, например:

```sh
node --test tests/test-profiles.mjs tests/test-profile-settings.mjs
```

Полный набор:

```sh
node tools/test.mjs
```

`npm test` дополнительно вызывает vendor-сборку через `tools/develop.mjs`.
Тестовый runner использует Node без shell/glob expansion. Фикстуры проверяют
схемы, изоляцию, API, ошибки и упаковку; они не подтверждают фактическую
приёмку установленного EDT, v8std, JAR, тестовых баз и UI Codex.
Каждый тестовый файл ограничен пятью минутами, весь прогон — восемью.
Внешний таймер работает в отдельном процессе: при зависании он завершает
принадлежащее прогону дерево процессов и возвращает ошибку до таймаута CI.
Упаковочные тесты собирают плагин во временной копии исходников и не заменяют
существующий каталог `.build` в рабочей копии.
Карта регрессионных и поведенческих проверок и их ограничения:
[ACCEPTANCE.md](ACCEPTANCE.md). Поведенческие сценарии выполняются отдельно
по `tests/behavioral/README.md`; Node runner не выдаёт их за автоматические тесты.
События, состояния и сценарии формы настроек перечислены в
[SETTINGS_UI_AUDIT.md](SETTINGS_UI_AUDIT.md).

### Дополнительные проверки разработки

Для восстановления инструментов после очистки `~/.codex` или переноса рабочей
копии на другой компьютер запустите `tools/setup-dev-tools.sh` двойным кликом
в проводнике. В Windows для этого должен быть установлен Git for Windows, а
файлы `.sh` должны открываться через Git Bash. Если ассоциации нет, выберите
Git Bash в меню «Открыть с помощью». Также можно запустить скрипт из Git Bash:

```sh
bash tools/setup-dev-tools.sh
```

Нужны доступ к сети, Node.js 24.11+ на ветке 24 или 26+, npm, Git и Codex CLI
в `PATH`. Скрипт пересоздаёт `node_modules/` из lockfile, подготавливает vendor,
устанавливает Chromium, обновляет индекс GitNexus с `--index-only`, настраивает
его MCP для Codex и запускает проверку MCP Inspector. Если папка Codex отсутствует,
скрипт создаёт её. Вход в учётную запись, удалённые настройки и установленные
плагины он не восстанавливает. Окно ждёт Enter перед закрытием; после ошибки
исправьте причину и запустите скрипт снова.

Существующее подключение `gitnexus`, настроенное иначе или отключённое, скрипт
не заменяет и сообщает об этом. Для стандартного подключения без собственного
таймаута он устанавливает `startup_timeout_sec = 180`; явно заданный таймаут
сохраняется. Сборку и публикацию плагина скрипт не выполняет.

GitNexus индексирует репозиторий локально. Для подключения MCP в Codex и
обновления индекса выполните из корня:

```sh
npx -y gitnexus@latest analyze --index-only
codex mcp add gitnexus -- npx -y gitnexus@latest mcp
npx -y gitnexus@latest status
```

Команду `codex mcp add` достаточно выполнить один раз в пользовательской
настройке Codex. Новый сервер может стать доступен только в новом сеансе.
Если запуск MCP занимает больше 10 секунд, задайте для сервера
`startup_timeout_sec = 180` в секции `[mcp_servers.gitnexus]` пользовательского
`~/.codex/config.toml`.
Используйте `--index-only`: обычный `analyze` и `setup` могут менять файлы
интеграции и hooks. Индекс `.gitnexus/` не включается в Git и поставку.
При работе с исходниками Codex сам проверяет актуальность индекса и при
необходимости обновляет его перед анализом и после изменений индексируемых
файлов. Постоянное фоновое обновление не включено. Результаты графа и
динамические импорты проверяйте по исходникам; предупреждение об усечённом
обходе означает, что отсутствие цепочки в индексе не доказывает её отсутствия
в коде.

Локальные инструменты устанавливаются вместе с dev-зависимостями:

```sh
npm run quality:mcp
npm run quality:dependencies
npx playwright install chromium
npm run test:ui
```

MCP Inspector подключается к серверу настроек в отдельном временном каталоге,
запрашивает `tools/list` и проверяет переносимость схем в строгом режиме.
Предупреждения печатаются, ошибки приводят к ненулевому коду. Эта проверка не
заменяет тесты операций `tools/call`. Правила dependency-cruiser проверяют
циклы и импорты из runtime-кода в `tests/` и `tools/`; существующие нарушения
тоже выводятся как ошибки. Граф строится статически и не подтверждает все
динамические зависимости.

Playwright запускает Chromium и тестовый хост MCP App с изолированными
временными профилями и настоящим stdio-сервером настроек. Сценарии проверяют
обмен `ui/initialize` и `tools/call`, сохранение и отмену, просмотр другого
проекта, ошибки и узкий экран. Ошибка сохранения имитируется хостом. Это не
проверка работы формы внутри Codex; для неё нужен настоящий хост и визуальное
ревью. Скриншоты и трассы тестов сохраняются в `test-results/`, который не
включается в Git или поставку.

Для документации сверяйте команды и поля с реализацией, проверяйте ссылки
и примеры YAML. При изменении состава поставки проверяйте оба архива и
извлечённый плагин. Сборка не является обязательным завершением каждой задачи.
В `docs/` описывайте действующие возможности, контракты, ограничения и порядок
работы. История разработки и перечни изменений относятся к Git.

Инструкции агенту в `AGENTS.md` и `skills/`, комментарии к коду и названия тестов
пишутся на английском. Пользовательская документация, интерфейс и сообщения
пользователю — на русском; имена API, ключи и значения контрактов сохраняются.
Проверка `tests/test-language.mjs` охватывает все навыки, заголовки документации,
пояснения схем и основные ошибки профиля. Она не заменяет ревью новых текстов.

## Локальная сборка

После установки dev-зависимостей выполните:

```sh
bash tools/build-plugin.sh
```

На Windows можно использовать Git Bash. Обёртка запускает только
`vendor.mjs` и `package-plugin.mjs`; при интерактивном запуске ждёт Enter
перед закрытием. Она не запускает тесты и ничего не публикует.
Эквивалент без Bash:

```sh
node tools/vendor.mjs
node tools/package-plugin.mjs
```

Сборщик проверяет входы, затем заменяет `.build/`. Не храните в ней нужные
ручные файлы. Результат:

```text
.build/
  marketplace/
    .agents/plugins/marketplace.json
    plugins/1c-ai-core/
  1c-ai-core-VERSION.zip
  1c-ai-core-VERSION-marketplace.zip
  SHA256SUMS
```

Первый ZIP содержит плагин в каталоге `1c-ai-core/`, второй — корень магазина
с каталогом `.agents/plugins/` и готовым пакетом. Внутри плагина сборщик
создаёт `.codex-plugin/plugin.json`, `build-info.json` и `SOURCE.md`.

Локальная версия выбирается как максимальная из версии `plugin.json`
и стабильных tags, достижимых из HEAD. Её можно задать явно:
`node tools/package-plugin.mjs --version 0.3.1` (пример версии).
Для tag-сборки CI версия обязана совпадать с tag. Сборщик не меняет
manifest исходников и отмечает dirty-состояние в build-info/SOURCE.

Проверьте извлечённый пакет:

```sh
node tools/check-plugin.mjs .build/marketplace/plugins/1c-ai-core
```

Проверка запускает MCP из готового пакета с Node-only окружением,
проверяет манифест, включённые зависимости, лицензии и операции с профилем.
Проверка извлечённого пакета также загружает поставляемые схемы знаний,
валидирует изолированный Markdown-каталог и форму подтверждения публикации,
проверяет отказ старой версии профиля. `schemas/*.json` включаются действующим
правилом package layout; smoke-matrix CI выполняет эту же проверку на Node 22/24
в Windows, Linux и macOS. Это локальная проверка контракта, без live-приёмки
OpenViking и без включения внешнего поиска.
Для проверки контрольных сумм ZIP и извлечения используйте
`node tools/verify-package.mjs .build .work/verified-package`;
путь вывода должен быть новым. После извлечения можно проверить
`.work/verified-package/plugins/1c-ai-core` тем же `check-plugin.mjs`.

Установите готовый магазин в Codex:

```sh
codex plugin marketplace add ./.build/marketplace
```

Затем установите плагин из этого источника. Codex использует установленную
копию в кэше, поэтому изменение исходников само по себе не обновляет
работающий плагин. После пересборки обновите локальный источник/установку
и перезагрузите её средствами хоста.

## Состав и лицензии пакета

Allowlist определяет `scripts/package_layout.mjs`. Пакет содержит runtime,
навыки, схемы, документацию, generic-профиль, vendor bundle и лицензии.
Не содержит `tools/`, `tests/`, `node_modules/`, Git, проектные профили,
локальные настройки и состояние пользователя. Bash-обёртка остаётся
в исходниках и не поставляется пользователю.

Обязательно сохраняются `LICENSE` (MPL 2.0), `NOTICE.md`,
`UNICODE-LICENSE.txt`, сгенерированные `vendor/NOTICE.txt` и `SOURCE.md`.
Сторонние компоненты сохраняют свои лицензии; сведения о происхождении
нельзя заменять общей лицензией плагина.

## CI и публикация

Workflow `build-plugin.yml` запускается для push в `develop` и стабильных
числовых tags вида `0.3.1` без префикса `v`. Pull requests и другие push веток
его не запускают. Публикация Stable принимает только tag, указывающий на
коммит в истории `main`.
Push-сборки одного ref выполняются по одной с очередью до 100 ожидающих
запусков.
При переполнении очереди GitHub отменяет дополнительные запуски. Порядок
начала выполнения не гарантируется GitHub, поэтому защита от отката при
публикации также обязательна.
CI устанавливает runtime-зависимости, собирает vendor, запускает регрессии,
проверяет ZIP и публикует artifact `1c-ai-core-plugin`. Затем smoke-matrix
проверяет извлечённый пакет на Windows/Linux/macOS с Node 22 и 24.

Сборка push в `develop` создаёт отдельный плагин `1c-ai-core-preview`
с названием `1C AI Core Preview` и версией, например, `0.4.3-preview.1`.
Базовая версия берётся из `plugin.json`; номер считает все push-запуски
сборки `develop` этой версии, включая неудачные. Повторный запуск сохраняет
номер, при изменении базовой версии счётчик начинается с 1. Для вычисления
нужны история workflow GitHub Actions и исходные коммиты этих запусков;
не удаляйте историю запусков и не переписывайте историю `develop`.
Совместимость профилей Preview проверяется по базовой версии.

`publish-marketplace.yml` получает успешную tag- или develop-сборку после завершения
всего workflow, проверяет её происхождение, revision, версию, run ID,
контрольные суммы и отсутствие dirty-состояния. Доверенные publication tools
берутся из main. Публикация обновляет только `ShadobaAI/codex-plugins`,
сохраняя остальные записи магазина и запрещая откат версии каждого канала.
Сборки могут завершаться не по порядку: Preview с меньшим номером не заменяет
Preview с большим номером независимо от порядка завершения проверок.
Stable и Preview находятся в магазине параллельно как независимые записи.

Для публикации нужен `MARKETPLACE_TOKEN` с Contents write к репозиторию
магазина. Это CI-секрет; пользователь плагина его не настраивает.
Ручной запуск публикации принимает ID успешной tag- или develop-сборки.
Для работы `workflow_run` workflow и publication tools должны находиться
в ветке по умолчанию `main`. Создание stable tag выполняется отдельно.
