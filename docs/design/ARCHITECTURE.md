# Архитектура универсального плагина разработки 1С

**Статус:** целевая архитектура для реализации.  
**Редакция:** 1, 19 октября 2026 года.  
**Область:** большие 1С-продукты, независимые Git-репозитории, несколько EDT-контуров и тестовых сред.

Плагин `1c-ai-core` предоставляет единый процесс анализа, проектирования, разработки, ревью, создания тестов YaXUnit и Vanessa, а также выпуска патчей-расширений. Основная единица работы — **workspace**, который объединяет репозитории, компоненты продукта, зависимости и состав проверяемых систем. CRM и Kafka подключаются декларациями своих рабочих пространств.

KORA определяет инженерное поведение: находить подходящее готовое решение, обосновывать добавляемую сложность, использовать достоверные факты и проверять фактический результат. Навыки управляют рассуждением агента; детерминированное ядро проверяет маршруты, полномочия, версии и выполнение операций. Собственный модельный оркестратор для этого не требуется.

## 1 Общая схема

Полная схема всех компонентов находится в [технической архитектуре](TECHNICAL_ARCHITECTURE.md#1-единая-техническая-схема). Это единственная каноническая схема плагина; ID компонентов, interfaces, настройки и пример workspace определены в том же документе.

Все линии к исполнителям проходят через проверку области и effects. На схеме показаны логические модули: ядро поставляется модульным приложением, без отдельного сервиса для каждого блока. Внешние EDT, code-index, BSL LS, v8std, OpenViking и тестовые среды сохраняют собственные жизненные циклы.

## 2 Архитектурные решения

| Решение | Следствие |
| --- | --- |
| Workspace объединяет независимые репозитории | Расположение внутри одного каталога не требуется; связь задаётся явно |
| Repository, checkout, component, EDT binding и assembly имеют разные идентификаторы | Выбор индекса не переключает writer; тестовая копия базы не подменяет production source |
| Один общий набор навыков и предметных модулей | CRM/Kafka задают состав продукта и правила, без собственных копий ядра |
| Источник факта определяется вопросом | Карточка помогает выбрать API; текущий контракт подтверждает соответствующий source/live authority |
| KORA встроена в сценарии работы | Поиск выполняется для нерешённой смысловой операции; достаточные факты переиспользуются |
| Готовность определяется зависимостями операции | Неисправность обязательной возможности блокирует зависимый шаг и его результат |
| 1С-исходники изменяются через назначенный EDT | Универсальные файловые инструменты работают с разрешёнными обычными файлами |
| Публикация знаний отделена от поиска | У поискового агента отсутствуют полномочия публикации и автоматического capture сессий |
| Межрепозиторное изменение оформляется одним ChangeSet | Сохраняются отдельные Git-истории и явное частичное состояние при отказе |
| Поставка ядра и ревизия знаний версионируются независимо | Обновление одного не объявляет автоматически готовым другое |

`1c-docs-mcp` и `1c-ssl-mcp` исключены, включая резервные подключения. Платформенная справка относится к EDT; возможности БСП — к опубликованным знаниям и проверке установленных контрактов. Это сохраняет принятые решения [каталога миграции](../../skills/catalog.yaml).

## 3 Модель мультирепозиторного пространства

### 3.1 Основные сущности

| Сущность | Что описывает |
| --- | --- |
| Workspace | Продукт или согласованную область разработки, граф компонентов, правила и допустимые среды |
| Repository | Логическую идентичность независимого репозитория и его роль: продукт, библиотека, тесты, framework, расширение, документация |
| Checkout | Физическую рабочую копию repository: canonical path, Git HEAD, ветку и значимые локальные изменения |
| Component | Конфигурацию, расширение, библиотеку, набор feature-файлов или иной артефакт с владельцем, происхождением и правилами сопровождения поставки |
| Dependency | Направленную связь компонентов: uses, tests, patches, composed_from; отдельно — разрешение чтения и изменения |
| EDT binding | Экземпляр EDT, обслуживаемый проект и соответствие его live-модели конкретному компоненту/checkout |
| Assembly | Проверяемый состав системы: базовая конфигурация, расширения, версии и существенные условия их совместной работы |
| Environment | Конкретную ИБ, платформу, способ запуска, manager/TestClient и допустимые эффекты |
| TaskContext | Цель, тип работы, критерии, риск L/M/H, доступные источники и разрешённую область текущей задачи |
| ChangeSet | Согласованный набор изменений, baseline, результатов и зависимостей в одном или нескольких repositories |

Repository может иметь несколько checkout. Один EDT обслуживает несколько проектов; одному проекту нельзя приписывать другую рабочую копию без подтверждённого binding. Component может использовать общий индекс канонического источника и одновременно проверяться в отдельной сборочной проекции. Такая проекция хранит ссылку на происхождение и состав; её live-состояние проверяется отдельно.

### 3.2 Пример связей

Продукт использует библиотеку; патч изменяет поведение продукта; тестовое расширение проверяет продукт и патч, используя отдельный YaXUnit framework. Production assembly включает продукт и патч; unit assembly добавляет framework и тестовое расширение; UI assembly проверяется feature-наборами Vanessa. Машиночитаемый пример этих связей приведён в [workspace.yaml](../../examples/multirepo-workspace/workspace-config/.ai/workspace.yaml).

В графе зависимостей связи направлены от потребителя или составной assembly к поставщику компонента: `consumer -> provider`. Роли `base`, `extension` и `test extension` уточняют включение в assembly. Наличие связи разрешает только объявленное чтение. Запись в библиотеку, framework или другой репозиторий требует включения этого владельца в scope задачи.

Индексы привязаны к canonical checkout. Сборочная копия `base` в unit-контуре может читать индекс канонической библиотеки, но её live authority остаётся назначенный EDT тестового контура. Это не переносит право source-записи с канонического владельца на read-only projection. Подготовка сборочной копии является отдельной разрешённой assembly-операцией над зафиксированными входами. При расхождении копии с каноническим источником общие индексные факты перестают подтверждать её live-контракт.

### 3.3 Декларации и локальные привязки

```text
workspace-config/
  AGENTS.md
  .ai/
    workspace.yaml            # repositories, components, dependencies, assemblies
    WORKSPACE.md              # назначение, правила, SDD/ADR и ограничения
    workspace.local.yaml      # локальные checkout и подключения; вне Git

любая рабочая копия/
  .ai/repository.yaml         # необязательная явная ссылка на workspace и repository

managed-state/
  installations/              # согласованные версии плагина и runtime locks
  workspaces/                 # bindings, evidence, операции и результаты
  sessions/                   # сессионные BSL LS и контекст хоста
```

Переносимая декларация содержит логические IDs, роли, относительные source roots внутри каждого repository, зависимости и требования совместимости. Локальные привязки разрешают checkout в разных каталогах и на разных дисках, URL конкретных EDT и ссылки на credentials. Секреты хранятся в предназначенном для этого хранилище; содержимое ключей не экспортируется.

Выбранный каталог разрешается в точный checkout и component. Если он относится к нескольким workspace, используется явный выбор сессии. Repository descriptor может ссылаться на workspace за Git-границей; это явная привязка, которую проверяют по реестру разрешённых расположений. Неявного заимствования родительского профиля или маршрута соседней папки нет.

Локальные overrides меняют расположения, подключения и параметры экземпляра. Они не ослабляют политику и не меняют автоматически владельцев компонентов. Несколько экземпляров одного checkout могут использовать разные EDT URL; совместная запись в одну физическую цель остаётся конфликтующим ресурсом.

## 4 Общее ядро

| Модуль | Ответственность |
| --- | --- |
| Workspace Registry | Разрешение workspace, repository, checkout и component; проверка canonical paths и явных разрешённых корней |
| Workspace Graph | Типизированные зависимости, разрешённые read scopes, состав assembly, порядок связанных изменений |
| Context Resolver | Привязка задачи к checkout, HEAD, локальным изменениям, EDT instance/project, индексам и среде |
| Capability Router | Выбор назначенного провайдера по вопросу, компоненту, версии и живому контракту |
| Readiness | Проверка необходимых возможностей и инвалидация только затронутых фактов |
| Action Policy | Проверка фактических effects, области задачи, правил проекта и реального пользовательского согласия |
| Evidence Store | Краткие факты с происхождением, покрытием, версиями и условиями актуальности |
| Operation Executor | Guards, ресурсные leases, единственный dispatch записи, отслеживание job и reconciliation |
| Result Store | Диагностики, diff, test receipts, manifest артефактов и итоговое состояние ChangeSet |
| Runtime и Release Manager | Установка, pin совместимых версий, health, обновление, миграция и восстановление |

Граф описывает существующие связи и исследованные факты. Полный граф всех динамических зависимостей крупной конфигурации не является условием первого выпуска. Автоматизация добавляется для конкретного нерешённого вопроса.

Контекст хранит только нужные задаче сведения. Evidence содержит `source`, `scope`, `revision/hash`, `coverage`, `observed_at` и условия инвалидации. Branch switch, изменение binding, релевантная запись, переиндексация, смена нормативного корпуса или публикации знаний инвалидируют соответствующие факты. Журнал операций сохраняет dispatch/job/outcome для восстановления; скрытые рассуждения и полные диалоги туда не записываются.

До dispatch мутации журнал фиксирует намерение, target, baseline, effects и ID операции. После сбоя между отправкой и сохранением ответа операция считается имеющей неизвестный исход. Сам журнал не обеспечивает exactly-once на внешнем сервере: повтор запрещён до reconciliation, а серверный idempotency key применяется только при подтверждённой поддержке.

## 5 Предметные модули и адаптеры

| Возможность | Назначенный исполнитель | Основной контракт |
| --- | --- | --- |
| Поиск исходников, структуры и потребителей | code-index | Ограниченный read-only запрос к точному canonical checkout с проверенным покрытием |
| Live-метаданные, текущий контракт и запись 1С | EDT adapter | Точные instance/project/component, guards и подтверждённый исход |
| Первичная диагностика модели | EDT adapter | Scoped baseline и сопоставимая post-validation |
| Дополнительная BSL-диагностика | BSL LS adapter | Root конкретного checkout; результат дополняет EDT |
| Платформенная справка | EDT adapter | Проверенная применимость к версии/контексту; пробелы не заполняются догадками |
| Выбор норм и compliance | Bundled policy + v8std | Детерминированная применимость и полный нормативный первоисточник |
| Поиск возможностей и опыта | OpenViking adapter | Разрешённая область, подтверждённая публикация, технический read-only |
| Создание YaXUnit-тестов | YaXUnit module + EDT | Отдельные владельцы тестов, продукта и framework; регистрация и изоляция данных |
| Создание Vanessa-тестов | Vanessa module + scoped files | Разрешённые feature roots, библиотека steps, assertions и данные |
| Выполнение тестов | YaXUnit/Vanessa execution adapters | Точная assembly/environment, согласованные effects и результаты того же запуска |
| Патчи-расширения | Extension module + EDT | База read-only, отдельный компонент расширения, совместимость и target guards |
| Упаковка CFE | Назначенный extension build adapter | Известный versioned build contract, проверенные входы и manifest результата |
| Обычные файлы и документы | Scoped file adapter | Только разрешённые неплатформенные файлы в scope задачи |
| Git | Scoped Git adapter | Точные repositories/refs; source diff получается через разрешённый source authority |

Адаптеры реализуют небольшой общий контракт: описание capabilities, проверку binding, readiness, выполнение ограниченного действия, статус длительной операции и получение результата. Реальные параметры EDT сверяются с поддерживаемой schema/guide; архитектура не предполагает одинаковой поверхности всех версий MCP.

Effects определяются доверенным адаптером по операции и target и проверяются общей политикой. Переданное моделью утверждение `read-only` не может изменить фактическую классификацию записи, запуска, cleanup или работы с данными. Неизвестная семантика блокирует действие до установления контракта.

Skills задают порядок работы и критерии решения. Read-операции получают минимальную область; мутации, запуски и сборки проходят Operation Executor. Плагин не требует превращать каждое рассуждение модели или каждый оператор BSL в отдельный вызов сервиса.

## 6 Знания и KORA

### 6.1 Контур знаний

```text
knowledge-git/
  bsp/
  projects/<project-id>/
  experience/
  catalog-manifest.yaml
```

Git определяет опубликованную редакцию карточек. Отдельный процесс проверяет контент, review и manifest, строит индекс OpenViking, проверяет добавления/изменения/удаления и только затем публикует подтверждённую пару `publication_revision + index_revision`. Непроверенный или частично обновлённый снимок агенту не выдаётся.

Поисковый адаптер ограничен разрешёнными коллекциями и полями. Он не синхронизирует Git с индексом во время чтения и не располагает публикационным ключом. Серверная/сетевая граница запрещает запись и чтение чужих областей также через прямые интерфейсы. При необходимости используется тонкий read-only gateway без собственного индекса.

Карточка содержит назначение, API, условия применения и отказа, существенный контракт, контекст, источник, compatibility и статус. Проектные обязательные обёртки имеют явную область действия. Опыт из CRM применяется в Kafka после проверки соответствия контексту. Текст карточки рассматривается как данные и не меняет полномочия агента.

### 6.2 Два контроля

**Переиспользование.** Для новой смысловой операции выбирается один из режимов: уже известное применимое решение; короткий поиск; углублённая проверка рискованного контракта. OpenViking находит возможность, code-index помогает исследовать реализацию и потребителей, EDT подтверждает необходимые live-факты. Одинаковая операция не исследуется повторно без инвалидации evidence.

**Достаточность.** Нетривиальная защита, обработка исключения, fallback, обёртка или расширение API должны закрывать требование, действительный контракт или достижимый существенный отказ. Проверка повторяется по diff. Права, безопасность, транзакции и проверки внешнего ввода сохраняются в необходимом объёме.

Новый код допустим при установленной несовместимости готового решения или достаточном ограниченном поиске в проверенной области. Пустая выдача не становится доказательством отсутствия API во всём продукте.

### 6.3 Готовность по зависимостям операции

Это **явное изменение глобального правила D-09 KORA 3.1**: блокируется зависимая инженерная операция, при этом остаются доступны независимые действия диагностики и восстановления. Для штатного проектирования и изменения поведения проверенный OpenViking остаётся обязательным.

| Работа | Участие OpenViking |
| --- | --- |
| Анализ расположения известного символа, текущей структуры или точного live-факта | Не требуется, пока результат не включает выбор нового решения или вывод о достаточности переиспользования |
| Проектирование и анализ вариантов решения | Обязателен для выбора возможностей; недоступность блокирует соответствующее решение |
| Разработка, authoring тестов и патча-расширения | Обязателен для выбора новой логики и подтверждения полноты workflow |
| Полное ревью решения | Обязателен для проверки пропущенного подходящего API; source-only анализ можно выдать с ограниченным scope без заключения о полном review |
| Запуск уже заданного теста или сборка уже зафиксированных входов | Не требуется, если операция не переходит к проектированию/исправлению |
| Диагностика окружения и reconciliation начатой записи | Не блокируется отказом поиска знаний |

При отказе OpenViking новые зависимые записи останавливаются. Уже начатая запись отслеживается до установленного исхода через её executor/EDT. Автоматического поиска по Markdown вместо OpenViking нет. Адресная работа с карточками по прямому запросу пользователя остаётся отдельной задачей и не объявляет готовым заблокированный workflow.

Readiness вычисляется как `ready`, только когда подтверждены все обязательные capabilities конкретного шага. `unknown` и отсутствие evidence не считаются успехом. Частично выполненная задача сохраняет результаты и точный blocker.

## 7 Сценарии работы

| Задача | Основной путь | Результат |
| --- | --- | --- |
| Анализ | Scope → граф → bounded source/live queries → сопоставление фактов | Ответ, карта влияния или исследование с источниками и пределами покрытия |
| Проектирование | Требования → KORA → нормы → варианты → риски и границы → план проверки | Соразмерная SDD; ADR при существенном архитектурном решении |
| Разработка | TaskContext → ChangeSet → proposal → guards → EDT/files → диагностика → tests → diff | Проверенные изменения в объявленных repositories |
| Ревью | Точные refs/diff → требования → impact → нормы → KORA → проверка поведения | Read-only findings с расположением, сценарием, последствиями и evidence |
| YaXUnit | Поведение → владелец тестов → fixtures/mock boundary → authoring через EDT → регистрация → scoped run | Тестовое расширение и результаты того же запуска |
| Vanessa | Business scenario → steps/data → feature → syntax → точный TestClient → scoped run | Feature-файлы, assertions, актуальные результаты и receipt |
| Патч-расширение | Контракт базы → выбор способа расширения → component → EDT → кандидат CFE → assembly tests → review → выпуск | Расширение, manifest совместимости, checksums и результаты проверки |

Тип работы является явной границей: анализ и ревью не разрешают исправления; написание теста не разрешает запуск ИБ. Разрешение, данное пользователем на те же scope/effects, переиспользуется. Уточнение требуется только для действительно недостающего решения, полномочия или расширения области.

L — локальная работа с доказанно низкими последствиями; M — изменение поведения; H — публичные контракты, схема, права, интеграции и иные существенные риски. Для L достаточно короткой постановки и точечной проверки. Для H нужны согласованный дизайн, необходимые проверки потребителей и независимое read-only ревью. Независимый агент используется при необходимости; простая задача не требует постоянной команды агентов.

YaXUnit framework имеет собственное read-only владение. Тесты не изменяют framework или production ради удобства mock. Vanessa фиксирует конкретную assembly, manager/TestClient и фактически исполненный текст. Успешная команда запуска, syntax-only или ноль выполненных тестов не являются passing behavior test.

## 8 Изменения в нескольких репозиториях

TaskContext фиксирует Read set и Write set, после чего ChangeSet сохраняет baseline, порядок зависимых изменений и guards владельцев. Проверка assembly объединяет diagnostics, tests и review. При отказе сохраняется точное частичное состояние для reconciliation; оно не объявляется принятым ChangeSet.

Read set и Write set задаются отдельно. Например, задача патча читает product/library/framework, пишет patch и согласованный test repository. Изменение публичного контракта библиотеки требует явного расширения Write set и проверки потребителей.

Каждое изменение сохраняет исходный HEAD и существенные guards. Ресурсный lease привязан к физической цели EDT/checkout, поэтому два разных alias не обходят блокировку одной цели. Leases координируют экземпляры плагина; от внешней записи человека защищает атомарный guard источника. Без него нельзя обещать отсутствие lost update.

Git-репозитории не получают общей транзакции. ChangeSet может быть частичным; ядро записывает, что применено, что не выполнено и какой результат неизвестен. После timeout writer не повторяется, пока не разрешён исход прежнего job. Восстановление не откатывает чужие изменения. Коммиты и публикация выполняются только в разрешённом пользователем scope.

Для совместного выпуска release manifest фиксирует точные ревизии/снимки repositories, состав assembly, версии проверенных контрактов, артефакты и test receipts. Установка расширения и изменение схемы/данных имеют отдельные эффекты и процедуры восстановления.

## 9 Патчи-расширения

Патч-расширение является самостоятельным компонентом с владельцем и жизненным циклом. Базовая поставка входит в Read set; код расширения — в Write set. Scope тестов и упаковки задаётся отдельно.

Жизненный цикл патча: требование → KORA и контракт базы → допустимый механизм расширения → отдельный component и EDT binding → изменение с guards/diagnostics → кандидат CFE → проверка целевой assembly и поведения → read-only review → выпуск того же проверенного CFE с manifest/checksums. Установка в конкретную ИБ требует соответствующего решения по effects.

Extension module проверяет применимость доступного механизма платформы, заимствование объектов, зависимости и взаимодействие с уже включёнными расширениями там, где это существенно. Факт создания исходных файлов не доказывает корректную adoption модели. Конкретные операции подтверждает установленный EDT contract.

Build adapter использует подтверждённую возможность EDT либо отдельно назначенный штатный инструмент 1С. Он получает зафиксированный снимок и разрешённое задание упаковки; отсутствие возможности блокирует сборку. Обход через произвольное редактирование сериализованных 1С-файлов не допускается.

Результаты приёмки связываются с SHA-256 кандидата CFE, составом assembly и состоянием тестовой среды. Проверка EDT-проекта до упаковки сама по себе не подтверждает выданный файл. При изменении входов или повторной сборке связь с прежними результатами пересматривается; финальная проверка должна охватывать именно выдаваемый артефакт.

Manifest артефакта содержит:

- ID и версию патча, цель и владельца исходников;
- точные входные ревизии/снимки и SHA-256 полученного CFE;
- требования к платформе, конфигурации, режиму совместимости и зависимым расширениям;
- проверенные контракты/отпечатки затронутых объектов базы и состав assembly;
- диагностики, связанные test receipts и результат review;
- инструкцию установки/удаления и отдельные условия для изменения данных.

Критерии совместимости проверяются при сборке и перед применением. Успех на одной версии базы не распространяется автоматически на другие. Удаление CFE не считается откатом преобразованных данных.

## 10 Полномочия и эксплуатационные границы

Агент получает scoped capabilities. Прямые writer-подключения, позволяющие обойти Action Policy и Operation Executor, отключаются в управляемом контуре. Credentials и доступ к endpoint исполнителей ограничиваются доверенными адаптерами. Host sandbox и серверные права дополняют проверки плагина; наличие hook не доказывает изоляцию.

Согласие фиксирует хост или доверенный UI-слой и связывает его с task/operation, target и effects. Модель передаёт ссылку на согласие; произвольный JSON с утверждением «пользователь разрешил» не является источником полномочий. Повторное согласование для уже разрешённого действия того же scope не требуется.

Source guards, разрешённые корни и tools scopes проверяются на фактически загруженном комплекте. Doctor выявляет конфликтующие старые MCP, hooks, auto-capture и смешанные версии. Он проверяет capabilities, необходимые выбранной операции, а также общую целостность и безопасность подключённого контура.

Тесты и сборка используют явно выбранные среды. Работа с общей прикладной ИБ не следует из разрешения создать код, тест или CFE. MCP служебных сведений общей ИБ является отдельной опциональной capability с собственными ограничениями; произвольные запросы, код и запись прикладных данных в её контракт не входят.

Локальное состояние содержит журнал операций, версии, ограниченные логи и receipts. Для каждой среды определяются владелец, допустимые данные, сроки хранения и процедура восстановления. Публикация знаний, runtime update и смена assembly не выполняются скрытым побочным эффектом поиска.

## 11 Поставка и жизненный цикл

```text
1c-ai-core/
  plugin/                     # manifest, host integration, skills, settings
  core/                       # workspace, graph, context, policy, evidence, operations
  domains/1c/                 # metadata, code, review, unit, ui, extension
  adapters/                   # EDT, code-index, BSL LS, v8std, OpenViking, runners
  contracts/                  # schemas и versioned adapter contracts
  runtime/                    # compatibility, verified artifacts, lifecycle
  release/                    # staging, migration, switch, rollback
  ui/                         # workspace setup, bindings, doctor, результаты
  tests/                      # contracts, negative cases, live acceptance, agent evals
```

Это целевое логическое разбиение. Выбор языка реализации и физических процессов фиксируется при проектировании модулей; существующие пригодные реализации можно сохранить за адаптерами.

Установка подготавливает согласованный пакет в staging, проверяет состав и совместимость, сохраняет принадлежащую плагину конфигурацию, выполняет проверки и переключает активную версию. При отказе восстанавливает подтверждённый комплект, не затрагивая чужие исходники и настройки. Runtime artifacts проверяются по digest и фиксируются совместимыми версиями; обновление проходит отдельную приёмку.

Независимо отслеживаются версия ядра, schema workspace, adapter contracts, runtime locks, ревизии исходников, assembly и пара knowledge Git/index. Перезапуск или переподключение восстанавливает операции по журналу, а readiness устанавливает заново для затронутых capabilities.

| Ресурс | Владение и жизненный цикл |
| --- | --- |
| code-index | Проверенный managed runtime; канонический checkout не индексируется повторно для каждой сборочной копии; доступ ограничен scope workspace |
| BSL LS | Сессионный процесс с несколькими штатно зарегистрированными конфигурациями внутри выбранного каталога; завершается вместе с клиентом |
| EDT и v8std | Подключения к предоставленным владельцем сервисам; старт и обновление требуют отдельно назначенного управляемого workflow |
| OpenViking и публикация | Командный инфраструктурный контур с разными правами поискового клиента и издателя |
| ИБ, manager и TestClient | Предоставленная среда; запуск, владение сессией и остановка явно учтены в effects |
| Builder CFE | Назначенный инструмент 1С с проверенной версией и разрешёнными входами/выходами |

## 12 Приёмка финального плагина

| Область | Наблюдаемый критерий |
| --- | --- |
| Мультирепо | Репозитории в разных каталогах; библиотека/framework доступны для разрешённого чтения; запись остаётся у назначенного владельца |
| Изоляция | Параллельные workspace, worktree и экземпляры одного checkout сохраняют свои bindings; конфликт одной физической цели обнаруживается |
| KORA | Подходящий API выбирается; похожий неприменимый отклоняется; новая логика и сложность соразмерны требованиям |
| Знания | Подтверждены разрешённый снимок, обработка удаления и read-only граница; отказ блокирует зависимый шаг без Markdown fallback |
| Анализ и дизайн | Ответ/SDD опираются на точные источники, не объявляют индекс live-истиной и не выполняют неразрешённые записи |
| Разработка | Проверены guards, baseline/post diagnostics, конфликт внешней записи, async job и неизвестный исход без повторного dispatch |
| Ревью | Read-only режим сохраняется; findings подтверждены конкретным сценарием, diff и source evidence |

| Патч-расширение | База сохранена; CFE получен из зафиксированных входов; именно этот артефакт проверен в целевой assembly |
| Межрепозиторный отказ | Сохранено точное частичное состояние; возобновление не повторяет сомнительную запись и не откатывает чужую работу |
| Поставка | Чистая установка, обновление, смешанная версия, отказ при переключении и rollback проверены; активен ожидаемый пакет |
| Пользовательский сценарий | Workspace подключается через UI, неоднозначные привязки подтверждаются, doctor объясняет blocker и способ восстановления |

Проверки включают контрактные тесты, негативные тесты границ, испытания на реальных EDT/ИБ и поведенческие пробы агента. Для итоговой приёмки выполняется пилот на CRM, Kafka и новом независимом мультирепозиторном проекте с измерением времени до принятого результата и качества изменений.

## 13 Порядок реализации

1. Workspace schema, идентичность checkout/component, explicit cross-repository dependencies и разрешение выбранного каталога.
2. Context, routing, capability readiness и scoped adapters поверх сохранённых пригодных runtime.
3. Operation journal, реальные согласования, guards, async/reconciliation и ChangeSet нескольких repositories.
4. Общие workflows KORA, Git-каталог, публикация и безопасный OpenViking; затем допуск зависимых задач.
5. Сквозные YaXUnit/Vanessa environments и extension workflow с упаковкой CFE.
6. Установка, миграция прежних окружений, UI, update/rollback и эксплуатационные проверки.
7. Приёмка всех сценариев, сопоставимый пилот и переключение проектов на единое ядро.

Подготовка схем и адаптеров может идти независимо. Выпуск для повседневной разработки требует одновременно готовых маршрутов, KORA-знаний, проверенной записи, тестовых workflows и процедуры восстановления.

## 14 Связь с исходными концепциями

[CORE.md](CORE.md) задаёт цель общего ядра и проектных привязок; [KORA 3.1](KORA_3_1.md) — контроль переиспользования, достаточности и достоверности знаний. Эта архитектура развивает их до workspace с независимыми репозиториями и явными assembly, добавляет ChangeSet и полный lifecycle патчей-расширений.

Глобальная блокировка KORA заменяется проверкой зависимостей операции, как определено в разделе 6.3. Исключение Help/SSL-MCP и общий принцип определения принадлежности поставки сохранены. Существующие профили и preset-деревья могут быть заменены новым контрактом без поддержки несовместимых форматов; миграция сохраняет проверенные проектные правила и реальные binding, а не прежнюю структуру файлов.
