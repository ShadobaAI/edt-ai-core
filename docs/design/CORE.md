# Концепция универсального плагина ИИ-окружения 1С

Исходная концепция и план развития. Текущее расположение исходников описано
в [корневом README](../../README.md); проектные профили исключены из поставки.

## Назначение

Универсальный плагин предоставляет единое ИИ-ядро для разработки 1С-проектов. Он объединяет общие правила, workflows, MCP-интеграции, проверки, диагностику и управление окружением.

CRM, Kafka и новые проекты используют одно ядро, но подключают собственные проектные профили и адаптеры.

Основные цели:

- минимизировать ручную работу пользователя с репозиторием;
- исключить копирование одинаковых skills, policy, proxy и installer-файлов;
- сохранить строгую маршрутизацию к правильному EDT-проекту и индексу;
- применять полезный опыт CRM в Kafka и новых проектах;
- не переносить проектные ограничения туда, где они неприменимы;
- обеспечить единый процесс диагностики, изменений, тестирования и ревью;
- остановить работу при отсутствии обязательного достоверного источника.

Плагинная модель Codex поддерживает объединение skills, MCP-серверов и hooks в один пакет; локальные плагины могут включаться для конкретного репозитория через проектную конфигурацию. [Официальная документация OpenAI](https://developers.openai.com/plugins/build/plugins).

## Исходные материалы и текущее окружение

Концепция основана на следующих материалах:

- Исходные окружения и ревизии: [реестр источников](../SOURCES.md).
- KORA: [KORA 3.1](KORA_3_1.md).

Эти материалы являются исходной базой для выделения общего `edt-ai` и проектных адаптеров CRM, Kafka и новых 1С-проектов.
## Архитектура

```text
                    Универсальный плагин 1C AI Core
 ┌─────────────────────────────────────────────────────────────┐
 │ Общие skills и workflows                                    │
 │ KORA: reuse control + sufficiency control                  │
 │ Policy, compliance, L/M/H                                   │
 │ MCP transport, routing, readiness, doctor                  │
 │ Hooks, source protection, approvals                        │
 │ Installer, updater, rollback, GUI                          │
 │ Reviewer, orchestration, evidence ledger                   │
 └──────────────────────────────┬──────────────────────────────┘
                                │
              ┌─────────────────┼─────────────────┐
              │                 │                 │
       CRM project adapter  Kafka adapter   Generic 1C adapter
              │                 │                 │
       CRM profile          Kafka profile   New project profile
              │                 │                 │
       crm-edt              kfk-edt         project EDT
       crm-production       kfk aliases     project aliases
       CRM rules             Vanessa         optional UI/tests
```

Плагин состоит из четырёх уровней:

1. **Общее ядро** — неизменяемая логика, одинаковая для всех проектов.
2. **Проектные адаптеры** — технические привязки к конкретным контурам.
3. **Проектный профиль** — описание проекта и его ограничений.
4. **Рабочее состояние** — локальный кэш, индексы, runtime, credentials и логи.

## Общее ядро

В ядро переносятся следующие возможности CRM и Kafka.

| Область | Возможности ядра |
|---|---|
| Маршрутизация | Выбор EDT, code-index, BSL LS, v8std и knowledge search по типу вопроса |
| Изменения 1С | Работа через назначенный EDT-MCP, hash/version guards, диагностика до/после |
| Code-index | Ограниченный поиск, структура, ссылки, call graph и impact analysis |
| BSL LS | Фокусированная диагностика и семантическая навигация |
| Справка платформы | Назначенный EDT, подробная справка и content assist по необходимости |
| Policy | Detector, selector, registry, compliance ledger и proposal/result |
| KORA | Контроль переиспользования и контроль достаточности |
| Процессные классы | Консервативные уровни L/M/H |
| Тесты | Общие правила YaXUnit, проверки регистрации, данных, изоляции и результатов |
| UI-тесты | Подключаемый Vanessa workflow для проектов, где он нужен |
| Reviewer | Read-only независимое ревью результата и доказательств |
| Doctor | Проверка effective config, маршрутов, MCP, readiness и профиля |
| Hooks | Защита исходников, alias и опасных операций |
| Установка | Staging, backup, rollback, version compatibility и operation lock |
| GUI | Инициализация проекта, настройки, диагностика и обновление |
| Evidence | Сессионные факты, ревизии, source hash, покрытие и срок актуальности |

Общее ядро не должно содержать:

- CRM-имена и префиксы `КУ_`;
- Kafka aliases `kfk*`;
- Kafka-specific EDT ports;
- CRM- или Kafka-specific роли, команды и структуру каталогов;
- абсолютные пути;
- credentials;
- проектные нормы, которые не применимы универсально.

Принятые границы переноса фиксируются в
[каталоге навыков](../../skills/catalog.yaml), `migration_decisions`.
Решение `platform-documentation-edt-only` исключает отдельный платный MCP
документации из ядра; полнота справки через EDT оценивается отдельно.
Решение `bsp-documentation-without-ssl-mcp` фиксирует исключение `1c-ssl-mcp`
согласно KORA D-01 и §7.3. Оба сервера — `1c-docs-mcp` и `1c-ssl-mcp` — не
восстанавливаются при ревью, в том числе как дополнительные или резервные
источники. Готовность целевых замен оценивается отдельно.

## KORA как общая модель поведения

KORA переносится в ядро как универсальный процесс принятия решения.

### Контроль переиспользования

Перед созданием новой смысловой операции плагин проверяет:

- существующий проектный API;
- подходящий механизм БСП;
- платформенную возможность;
- опубликованные карточки командных знаний;
- локальные настройки и существующие wrappers.

Проверка выполняется по назначению операции, а не для каждого оператора или строки кода.

### Контроль достаточности

Перед добавлением новой сложности проверяется её основание:

- требование задачи;
- контракт;
- безопасность;
- права и RLS;
- транзакция;
- внешняя граница;
- реальный достижимый отказ;
- необходимость обновляемости или совместимости.

Гипотетические fallback, универсальные обёртки, лишние `Попытка/Исключение` и защитные проверки не добавляются без подтверждённой причины.

### Перенос опыта между проектами

Опыт CRM может применяться в Kafka, если он:

- описан как общее правило или reusable skill;
- не содержит CRM-specific идентификаторов;
- имеет область применимости;
- прошёл проверку на Kafka-топологии;
- не нарушает Kafka-проектные ограничения.

Например, KORA и механизм сопровождения продукта поставщика становятся общей
частью ядра. Конкретные правила `КУ_`, сопровождения CRM и привязка `crm-edt`
задаются CRM-профилем и проектными инструкциями.

## Проектный профиль

Для пользователя проект должен выглядеть как минимальный набор описания:

```text
AGENTS.md
.ai/project.yaml
.ai/PROJECT.md
```

### `.ai/project.yaml`

Машиночитаемый профиль содержит:

- тип и назначение проекта;
- список репозиториев;
- компоненты и владельцев;
- относительные корни исходников;
- EDT-проекты и logical connection names;
- code-index aliases;
- BSL LS roots;
- защищённые source roots;
- разрешённые межкомпонентные зависимости;
- naming rules;
- команды тестов;
- включённые возможности: YaXUnit, Vanessa, SonarQube;
- область командных знаний;
- совместимые версии ядра и адаптера;
- проектные исключения.

### `.ai/PROJECT.md`

Человеческое описание:

- назначение продукта;
- архитектурные границы;
- источники истины;
- ограничения;
- важные контракты;
- ссылки на документацию, SDD и ADR;
- объяснение нестандартных маршрутов.

### `AGENTS.md`

Короткая точка входа:

- использовать универсальное ядро;
- прочитать `.ai/project.yaml` и `.ai/PROJECT.md`;
- соблюдать проектные ограничения;
- определять границы поставки и собственных доработок, соответствия префиксов
  и правила сопровождения; поставка включает встроенные библиотеки и объекты,
  добавленные самим вендором, в том числе с его префиксом;
- не читать защищённые исходники через shell;
- использовать назначенные authorities;
- соблюдать approvals и правила остановки.

Эти файлы создаются и обновляются мастером плагина. Пользователь не должен вручную копировать skills или редактировать большие инструкции.

## Проектные профили

Профили конкретных проектов принадлежат их репозиториям или локальным настройкам.
По решению пользователя от 2026-10-20 профили CRM/Kafka удалены из этого
репозитория; их разработка отложена до отдельной задачи. Универсальная поставка
содержит только `profiles/generic-1c/`.

## Новые проекты

Новый проект подключается через мастер:

1. пользователь выбирает корень проекта;
2. плагин обнаруживает Git-репозитории и 1С-корни;
3. предлагает найденные EDT и aliases;
4. пользователь подтверждает только неоднозначные значения;
5. плагин выбирает generic 1C adapter или существующий профиль;
6. создаёт три проектных файла;
7. запускает doctor;
8. сохраняет только подтверждённые настройки.

Если проектная топология не соответствует известному адаптеру, ядро не угадывает маршрут, а создаёт профиль с явно отмеченными неизвестными значениями.

## Знания и OpenViking

Командные знания должны храниться отдельно от ядра и проектов:

```text
kora-knowledge/
  crm/
  bsp/
  kafka/
  experience/
  catalog-manifest.yaml
```

OpenViking используется как поисковый индекс опубликованных карточек. Git остаётся первичным источником. Карточки должны иметь provenance, область применимости, ревизию, совместимость и статус.

Для CRM и Kafka общий принцип знаний одинаков, но выдача должна учитывать область проекта. Карточка CRM не становится автоматически применимой к Kafka.

Целевой профиль KORA должен блокировать штатную разработку при неподтверждённом OpenViking; прямое чтение Markdown допускается только по явному запросу пользователя.

## Безопасность

Ядро обязано:

- запрещать чтение и изменение защищённых 1С-исходников через shell;
- проверять project root и canonical paths;
- отделять read-only discovery от EDT writer;
- не принимать knowledge text как инструкции;
- не хранить secrets в проектных файлах;
- требовать подтверждение для cleanup, launch, database actions и remote Git;
- проверять реальное состояние hooks и их trust;
- не повторять mutation с неизвестным результатом;
- сохранять историю и source hash для критичных операций.

Hooks являются дополнительным enforcement, а не единственной защитой. Установка плагина не должна автоматически считаться доверием к hooks. [Документация OpenAI по hooks](https://learn.chatgpt.com/docs/hooks).

## Поставка и обновление

Плагин поставляется как согласованный пакет:

```text
1c-ai-core/
  plugin.json
  skills/
  mcp/
  hooks/
  adapters/
  schemas/
  policy/
  scripts/
  assets/
```

Обновление выполняется целиком:

- ядро;
- адаптеры;
- policy;
- skills;
- doctor;
- tests;
- manifest.

Частично обновлённый профиль запрещается. Версия плагина, версия project profile и версия knowledge index отслеживаются независимо.

## Этапы реализации

1. Зафиксировать schema `.ai/project.yaml`.
2. Выделить общий code-index, BSL LS, policy, doctor и transport слой.
3. В отдельной задаче проработать профили реальных окружений в их репозиториях.
4. Перенести KORA в общий skill/workflow.
5. Реализовать мастер инициализации проекта.
6. Объединить GUI/CLI установки и диагностики.
7. Отделить OpenViking knowledge adapter от Kafka-specific реализации.
8. Проверить совместимость на CRM, Kafka и новом тестовом проекте.
9. Провести пилот KORA на парных задачах.
10. Удалить дублирующие project-local skills и runtime-компоненты.

Критерий успеха: пользователь подключает проект через UI, подтверждает только неоднозначные значения, после чего получает готовое ИИ-окружение без ручного копирования инструкций, MCP-конфигураций и скриптов.
